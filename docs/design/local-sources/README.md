# Дизайн: локальные источники (git-репозитории вне GitHub и сессии Claude Code)

Статус: **архитектура, код не написан**. Дата: 2026-09-18.
Как получен: исследование (6 направлений) → панель из трёх независимых архитектур с тремя
судьями → два круга адверсариальной проверки (буквальная симуляция алгоритма выбора, сверка с
кодом и с документацией Cloudflare/git/Claude Code, поиск утечек, проверка полноты). Первый круг
нашёл 3 блокера и 39 серьёзных замечаний, второй — 0 блокеров; всё внесено в текст. Что осталось
непроверенным — помечено явно. Документ задаёт архитектуру и контракты; property-тесты
алгоритма выбора — обязательная часть I1.

## Зачем

Отчёт видит только GitHub. Работа, которая туда не попадает, теряется:

- репозитории, чей единственный remote — self-hosted forge (Forgejo/Gitea/GitLab), в том числе
  доступный только из приватной сети — Worker до него не достучится в принципе;
- репозитории вообще без remote;
- работа в сессиях Claude Code (в т.ч. без единого коммита).

Замер на машине автора: один forge-only репозиторий — ~50 коммитов и ~15 тыс. строк за неделю,
которых в отчёте нет. Почти половина человеческих промптов в Claude Code за ту же неделю — в
репозиториях, которых отчёт не видит.

## Решение в одном абзаце

На машине разработчика работает маленький кроссплатформенный **collector** (TypeScript, Bun,
ноль runtime-зависимостей). Он сканирует папки, находит git-репозитории, читает `git log` и
(опционально) метаданные сессий Claude Code и **пушит сырые датированные события** на Worker:
`PUT /ingest/v1/<machineId>`. Worker кладёт снимок в KV как есть (один ключ на машину,
скользящее окно 35 дней, идемпотентная перезапись). В недельном прогоне Worker сам выбирает
события своего окна, дедуплицирует, вливает в `WeekActivity` **до** `applyPrivacy` — и дальше
весь существующий конвейер (приватность, LLM-guard, часы, ачивки, отчёт, state, Telegram)
работает как раньше.

```
 машина разработчика (1..N)                         Cloudflare Worker
┌──────────────────────────────┐             ┌─────────────────────────────────────┐
│ collector (bun run collector)│   PUT       │ /ingest/v1/<machineId>              │
│  ├ git-local                 │ ─────────►  │   токен INGEST_TOKEN, тело не       │
│  └ claude-code (opt-in)      │  снимок     │   парсится; KV, TTL 45 дней         │
│ scan → snapshot → push       │  35 дней    └──────────────┬──────────────────────┘
└──────────────────────────────┘                            │ cron / /run
                                                            ▼
   GitHub API ──► collectWeekActivity ──► selectLocal + merge ──► applyPrivacy ──► …
                                          (ledger в AppState)      (как сейчас)
```

## Что получит пользователь с настройками по умолчанию

Честно и заранее: при `PRIVATE_REPOS=redact` (значение по умолчанию) локальная работа появится
в отчёте как `private-project-N` — **счётчики, строки, часы, ачивки, но без названий и без
текстовых сводок**. Текст коммитов с машины при этом вообще не уходит (`share: "counters"`).

Осмысленные сводки по локальным репозиториям — это три осознанных шага:
`share: "text"` на нужный хост + `PRIVATE_REPOS=full` + **приватный** reports-репозиторий
(Worker проверяет приватность сам и без подтверждения текст отбрасывает; collector без
подтверждения его даже не отправляет).

## Зафиксированные принципы

1. Собирает локальный скрипт, отчёт строит Worker (LLM, приватность, state, Telegram).
2. По сети идут **сырые датированные события**, не недельные агрегаты. Окно `[since, until)`
   определяет только Worker — иначе ломаются catch-up (до 4 недель), `?date=` и откат
   `DELETE /state/latest`.
3. Политика приватности и скраббинг секретов авторитетны на Worker'е; collector дублирует
   скраббинг на клиенте и по умолчанию вообще не отправляет текст.
4. Проект публичный: пока не задан `INGEST_TOKEN`, поведение не меняется (кроме явно названных
   исправлений I0); включение — несколько шагов у любого разработчика.
5. Один кроссплатформенный скрипт вместо скриптов под каждую ОС. ОС-специфично только расписание.

## Журнал решений

| Дата | Решение | Почему |
|---|---|---|
| 2026-09-18 | Локальный collector пушит, Worker строит отчёт | Worker не видит ни приватную сеть, ни диск; у Worker'а уже есть приватность, LLM-guard, state, undo |
| 2026-09-18 | Транспорт: `PUT /ingest/v1/<machineId>` → KV, один ключ на машину, перезапись | Идемпотентно; ноль внешних subrequest'ов; очередь не годится (сообщение ≤ 128 KB). Git-как-транспорт отклонён: приватные данные навсегда в истории GitHub, катастрофа при публичном reports-репо |
| 2026-09-18 | Сырые события + окно на Worker'е; снимки не удаляются при чтении (только TTL) | Undo, `?date=`, catch-up пересобирают неделю из тех же данных |
| 2026-09-18 | Ingest не парсит тело; валидация — в прогоне и в collector'е (общий рукописный guard) | Роуту под токеном с dev-машины парсинг не нужен — он остаётся тривиально дешёвым и ограниченным. Guard в ~10 раз дешевле zod и не тянет зависимость в collector. *(Это не «ради Free-плана»: лимит 10 мс на Free действует и на cron — см. вопрос 1)* |
| 2026-09-18 | Выбор событий — ledger учтённых коммитов внутри append-only `AppState`; **GitHub-коммиты прогона тоже пишутся в ledger** | Watermark на машину задваивает неделю в сценарии «две машины» и молча теряет опоздавшее. Без GitHub-записей зеркало forge → GitHub задваивалось бы неделей позже (проверено симуляцией) |
| 2026-09-18 | Дедуп: SHA глобально, затем `K = секунда автора + additions + deletions` в пределах репозитория | Только SHA: rebase-копии задваиваются. Только «секунда автора»: на машине автора теряет 5.4% реальных коммитов. `K` дал ровно «SHA минус rebase-копии» |
| 2026-09-18 | Лимит — один, на прогон, **старые первыми**, масштабируется на длину catch-up; несгоревшее откладывается, сгоревшее показывается счётчиком | «Новые первыми» навсегда теряет самые старые отложенные коммиты (симуляция: 49 из 196 на 4-недельном catch-up) |
| 2026-09-18 | «Полов» на машину нет: всё ни разу не учтённое за 28 дней учитывается и помечается опоздавшим; первый прогон с фичей начинает с `since` | Одна последовательная политика вместо трёх разных (новая машина / новый корень / гонка первого push с cron). Кто не хочет всплеска — `notBefore` в конфиге collector'а |
| 2026-09-18 | Область сбора — белый список `host[/namespace]`; GitHub-репозитории пропускаются | Скан `~` не должен утащить GitLab работодателя в личный отчёт; на общих SaaS-forge хоста мало — нужен префикс пространства имён |
| 2026-09-18 | Любой локальный репозиторий — `isPrivate = true`; политика — единственная ручка `PRIVATE_REPOS` | У локального репо нет проверяемого флага видимости; fail-closed как в `repo-visibility.ts` |
| 2026-09-18 | Текст локальных репо и заголовки сессий публикуются, только если Worker подтвердил приватность reports-репозитория; collector перед каждым push спрашивает это probe-запросом и без подтверждения понижает до счётчиков | Самая опасная комбинация — `text` + `full` + публичный reports-репо — иначе проходила бы молча |
| 2026-09-18 | Снимок помечен отпечатком токена; ротация обесценивает всё присланное старым токеном. Индекс машин вместо `list`, регистрация — только после успешной записи, прогон чистит индекс | Иначе после утечки подложенные машины жили бы 45 дней и навсегда занимали слоты; `list` на пути ingest дал бы держателю токена способ исчерпать квоту, на которой стоит `loadState` |
| 2026-09-18 | `INGEST_TOKEN`: отдельный, необязательный, вне `secrets.required`; умеет только писать | Токен живёт на dev-машинах. Цена решения: секрет не типизируется `wrangler types` и **не подхватывается `wrangler dev` из `.dev.vars`** — см. [05](05-operations.md) |
| 2026-09-18 | git: `-z` и NUL-разделители, `--shortstat`, типизированный набор команд, окружение из белого списка, `GIT_NO_LAZY_FETCH=1`, partial-clone пропускаются | Любой другой разделитель подделывается телом коммита или e-mail'ом автора; lazy fetch во враждебном partial-clone исполняет чужой код при простом `git log` (оба факта проверены фикстурами) |
| 2026-09-18 | Ядро collector'а — на `node:*` + `fetch`, ноль зависимостей; запуск из выделенного клона форка; конфиг — обычный JSON; токен и `machineId` — в каталоге состояния, не рядом с конфигом | Тестируется vitest под Node; `~/.config` часто лежит в dotfiles-репо — общий `machineId` заставил бы машины затирать снимки друг друга |
| 2026-09-18 | Сессии: на провод — метки человеческих промптов (минуты), ключ проекта, опционально заголовок; метрику считает Worker; отдельная строка, не часы | Все коммиты автора лежат внутри интервалов сессий — сложение дало бы двойной счёт; значение метрики зависит от определения, поэтому оно живёт в одном месте |
| 2026-09-18 | Отложено: Worker тянет данные сам (туннель), local-first, collector forge-API в Worker'е, хуки Claude Code, бинарники, общий интерфейс адаптеров | Туннель = демон + машина онлайн в момент cron; local-first не убирает транспорт между машинами; forge-API не покрывает no-remote и сессии; `SessionEnd`-хук — таймаут 1.5 с; для двух источников хватит двух модулей |

### Принятые допущения (дёшево изменить)

- Один общий `INGEST_TOKEN`; токены на машину — I5, без изменения wire.
- I3 (сессии) раньше I4 (установка расписания): автору ценнее сессии.
- Запуск из клона; npm-пакет — только если попросят.
- Неделя только с сессиями, без коммитов, активной не считается (streak не трогаем).
- Порядок репозиториев в отчёте при включённой фиче — по дате последнего коммита.

## Совместимость с roadmap

Анонсированные «тренды по неделям» и «месячные/годовые ретроспективы» этим дизайном не
блокируются, но важно, что считать долговечной единицей: **недельный агрегат + markdown-отчёт**.
Сырые события эфемерны по замыслу (KV 45 дней, транскрипты Claude Code 30 дней), а данные
сессий, в отличие от git, задним числом не восстановить. Поэтому I1/I3 пишут в `WeekSnapshot`
необязательные `localCommits?` и `aiPairingMinutes?`. Что ещё сохранять понедельно (например,
часы) и где хранить агрегаты дольше 52 снимков state — вопрос дизайна ретроспектив, не этого. См. [../../ROADMAP.md](../../ROADMAP.md).

## Открытые вопросы к владельцу

Только то, что нельзя выяснить из репозитория и замеров.

1. **Поддерживаем ли официально Workers Free?** Лимит 10 мс CPU на Free действует и на cron, и
   на consumer очереди; разбор снимков в прогоне его, скорее всего, превысит. Варианты:
   (а) локальные источники требуют Workers Paid — так и пишем в README; (б) отдельный
   Free-профиль (только счётчики, меньше лимиты). Сначала замер I0.
2. **Глубина сессий в отчёте:** только время · время по проектам + «сессии без коммитов»
   (предлагаю как цель I3) · плюс заголовки сессий (`aiTitle`, opt-in; это пересказ промпта
   моделью — может содержать имена клиентов; до 45 дней в KV).
3. **Вернуть уже потерянные недели?** Рецепт есть ([05](05-operations.md)): откаты state +
   `?date=` по неделям; перезаписывает старые отчёты, заново шлёт Telegram, стоит LLM-вызовов.
   Без `push --window-days` окно возможности ~5 недель от даты работы.
4. **Текст коммитов приватных репо в KV до 45 дней** (при `share: "text"`, после скраббинга) и
   хеши ledger в 52 снимках state (~год) — приемлемо?
5. **Определение «времени в паре с ИИ».** Предложение: промпты с паузой ≤ 15 мин — один
   интервал `[первый промпт, последний + 5 мин]`. На неделе автора это ~16 ч; чистое объединение
   без склейки — ~12 ч. Показывать ли вторым числом время работы агента без присмотра?
6. **Публикуем `docs/ROADMAP.md`** и в каком порядке идут пункты: локальные источники, тренды,
   ретроспективы?
7. **Нужна ли видимость «public» на хост** (для тех, у кого открытая работа на Codeberg/GitLab и
   публичный reports-репо)? Сейчас единственный путь к тексту — глобальный `full`.
