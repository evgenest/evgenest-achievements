# 05. Эксплуатация

> **Для кого:** владелец Worker'а — как пользоваться локальными источниками после первой установки и что делать каждую
> пятницу, пока I1 не вышла.
> **Что здесь решает владелец:** ничего нового. От пункта №4 общего списка («грейс») зависит одно: нужен ли
> `collector push` после каждого отката. Вопросы — только в [общем README](../README.md).
> **Что просто к сведению:** всё остальное. Все имена и адреса — заполнители.

## Обновление

Порядок всегда один: **сначала Worker, потом машины.**

1. Задеплоить Worker.
2. На каждой машине обновить выделенный клон collector'а до нужного закреплённого коммита (позже — тега релиза).

`push` читает `supported` из ответа на проверочный запрос и завершается с понятной ошибкой, если его схемы там нет.
404 от `/ingest/v2` → откат на `v1`; 404 от `v1` → функция выключена. Worker терпим к незнакомым полям (считает их в
сноску), поэтому collector чуть новее Worker'а данные не теряет.

## Токен: создание и ротация

Значение секрета из Cloudflare прочитать нельзя — поэтому сначала сохранить, потом отправить.

```
T=$(openssl rand -hex 32)
printf %s "$T" | wrangler secret put INGEST_TOKEN -c wrangler.prod.jsonc
D="${XDG_STATE_HOME:-$HOME/.local/state}/achievements-collector"
( umask 077; mkdir -p "$D"; printf %s "$T" > "$D/credentials" )
unset T
```

Без `-c wrangler.prod.jsonc` секрет уйдёт Worker'у с именем из шаблона. На остальные машины токен переносится вручную.
`INGEST_TOKEN` не должен совпадать с `RUN_SECRET` — Worker это проверяет и выключает приём.

Что токен умеет: записать снимок своей машины и **прочитать список учтённого** — короткие хеши учтённых коммитов,
границы и время двух последних прогонов. Текст, имена, state и чужие снимки ему недоступны, запустить прогон он не
может. Полная таблица — в [08-threat-model.md](08-threat-model.md).

Ротация (в том числе после утечки):

1. Та же команда — новый токен; обновить `credentials` на каждой машине. Пока машина шлёт старый токен, она получает
   403; **данные не теряются** — источник истины для текста — git на машине, следующий успешный push принесёт
   неучтённое не старше `from` (~28 суток; оно придёт с пометкой «опоздавшие»). Более старое — известный предел,
   S14 в [07-selection](07-selection.md#сценарии).
2. Снимки, присланные старым токеном, прогон отбросит и снимет сам (отпечаток токена в метаданных). Список учтённого
   от токена не зависит — переустанавливать нечего. Проверить: `GET /ingest`; незнакомые `machineId` удалить маршрутом
   `DELETE`.
3. Если прогон **уже прошёл** с подложенными данными — откат и перезапуск (раздел ниже).
4. Экстренно выключить функцию: `wrangler secret delete INGEST_TOKEN -c wrangler.prod.jsonc` — `/ingest*` станет 404;
   оставшиеся снимки сами истекут не позже чем через 9 суток, сразу — командами `wrangler kv … --remote` ниже.

## Машины

Машина — это клон collector'а, конфиг, файл `credentials` и случайный `machine-id`; настройки репозиториев на каждой
машине свои.

- **Добавить вторую:** клон, конфиг, `credentials`, push. `machine-id` создаётся сам. В первый отчёт придёт до 28 дней
  ни разу не учтённой работы с этой машины как «опоздавшая». Ручки «не раньше даты» (`notBefore`) больше нет: чего не
  хотите видеть — переведите в `off` **до** первого push.
- **Режимы на нескольких машинах.** Побеждает самое строгое правило: есть копия `counters` — репозиторий идёт цифрами.
  Но `off` Worker увидеть не может (с такой машины ничего не приходит), поэтому `off` ставится на каждой машине, где
  лежит этот репозиторий. *Принятое допущение:* `doctor` печатает короткий отпечаток набора правил — для сравнения машин.
- **Поправить по результату.** Отчёт вышел блёклым или лишне подробным → `collector set <папка> <режим>` → `push` →
  откат → перезапуск. Недели, учтённые раньше последней, не переигрываются.
- **Убрать:** `curl -X DELETE -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/ingest/v1/<machineId>`.
  Иначе ключ держит один из пяти слотов, пока не истечёт срок жизни снимка (9 дней) и ближайший прогон не снимет
  запись из индекса.
- **Посмотреть:** `curl -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/ingest`.
- Вручную через wrangler (обязательно `--remote`, иначе команда работает с локальным хранилищем и «успешно» ничего
  не делает):

```
wrangler kv key list   --binding STATE --prefix ingest:v1: --remote -c wrangler.prod.jsonc
wrangler kv key delete 'ingest:v1:<machineId>' --binding STATE --remote -c wrangler.prod.jsonc
```

- После ручного удаления ключа запись в индексе снимет ближайший прогон; маршрут `DELETE` делает оба действия сразу.
  Ключ `ingest:v1:accounted` руками не править: удалённый список Worker восстановит сам (до этого машины пришлют
  полное окно), а испорченный остановит push'и до ближайшего прогона — collector не разберёт ответ.
- Машина, получившая 409 (слоты заняты), завершает `push` с ненулевым кодом и строкой в stderr даже при `--quiet` —
  смотрите журнал расписания.
- Не синхронизируйте каталог состояния collector'а между машинами: общий `machine-id` заставит их затирать снимки
  друг друга. Там же лежат `credentials` (и `aliases.json`, если словарь когда-нибудь появится) — права 0600, не в
  `~/.config`; `doctor` считает ошибкой любой из этих файлов внутри git-дерева.

## Маршруты владельца

Все под `RUN_SECRET`, токену с машины недоступны; новые появляются в I1, два существующих меняют ответ.

| Маршрут | Назначение |
|---|---|
| `GET /ingest` | Индекс машин + метаданные снимков (без значений) |
| `GET /ingest/preview[?date=][&github=1]` | Пробный выбор: показывает, что взял бы **следующий** прогон, и не пишет ни отчёта, ни state (уже учтённых коммитов в снимках нет — нет их и здесь). По каждой машине: годен ли снимок (иначе код причины), **полон он или собран до отката**, сколько коммитов выбрано, сколько из них опоздавших, сколько отложено, сгорело, отброшено как дубль. По умолчанию GitHub не запрашивается, поэтому колонка «отброшено как GitHub» помечена «неполно»: в ней только коммиты, уже записанные в журнал с пометкой `gh:`. С `github=1` Worker дополнительно запрашивает у GitHub коммиты недели. Текста не возвращает. Единственное, что маршрут может записать, — поправить устаревший список учтённого |
| `DELETE /ingest/v1/<machineId>` | Убрать машину: ключ + запись в индексе |
| `DELETE /state/latest` | Сегодня отвечает `{ deleted }` (`src/index.ts:74-79`). Станет: `{ deleted, current, until, rerun: "/run?date=YYYY-MM-DD", accounted: { basis, through, entries } \| null }`; заодно переписывает список учтённого. `until` и `rerun` появляются уже в I0-минимум |
| `POST\|GET /run[?date=][&force=1]` | Только при заданном `INGEST_TOKEN`: предпроверка полноты снимков. **409** `{ error: "local_snapshots_stale", machines, hint }` или **202** `{ status: "accepted", warnings? }` |

## «Где мои коммиты?»

Четыре шага от машины к отчёту; чаще всего хватает первого.

1. `bun run collector scan` — таблица «режим / почему / коммиты / репозиторий / папка» и строка «сервер принимает
   текст: да | нет, потому что …». `scan --explain <путь>` — причины по одному репозиторию: чужой e-mail, вне окна,
   merge, необъявленный сервер, GitHub-remote, неполный клон, режим `off`, **уже учтён**.
2. `bun run collector push --dry-run` — ровно те байты, что уйдут. Учтённых коммитов в снимке нет — это норма.
3. `GET /ingest/preview` (под `RUN_SECRET`) — что Worker выбрал бы в следующем прогоне: по машинам — годен ли снимок,
   полон ли он, выбрано, опоздавших, отложено, сгорело, отброшено как дубль. Без модели, без записи отчёта и state.
4. Сноска в отчёте: опоздавшие, отложенные, сгоревшие; машины, молчащие > 48 ч; отклонённые и неполные снимки;
   причина, по которой скрыт текст.

## Откат и перезапуск

Привычная рутина «снять последний прогон, сменить модель, собрать ту же неделю заново» работает сразу, без ожидания
push, — за это отвечает «грейс» ([07-selection.md](07-selection.md)).

```
1. curl -X DELETE -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/state/latest
     → 200 { "deleted": "state:…", "until": "…", "rerun": "/run?date=YYYY-MM-DD", … }
2. (по желанию) сменить LLM_MODEL и задеплоить
3. curl -X POST -H "Authorization: Bearer <RUN_SECRET>" "https://<worker-url>/run?date=<день из rerun>"
     → 202 { "status": "accepted" }     либо     409 { "error": "local_snapshots_stale", "machines": ["m-…"], "hint": "…" }
```

- **Всегда с `?date=` из ответа `DELETE`.** Без него `until` = «сейчас»: неделя получится другой и появится второй
  файл отчёта. Сразу после удаления KV до ~60 с может показывать удалённый снимок; защита — I0-минимум: ответ 409 при
  `until ≤ lastRunUntil` и при ручном прогоне с периодом короче суток, и та же проверка внутри `runWeekly` — прогон из
  очереди, увидевший устаревший state, выходит без единой записи (в логе `run_skipped_stale_state`).
- **Одиночный откат** — перезапуск идёт по тем же снимкам: текст последней отчитанной недели в них ещё лежит. Если push
  успел пройти между шагами 1 и 3, снимок содержит больше нужного — тоже работает.
- **409 `local_snapshots_stale`** значит: снимки перечисленных машин собраны до отката и неполны (обычно это второй
  откат подряд). Что делать: `bun run collector push` на этих машинах или подождать до часа, затем повторить; свежий
  push виден предпроверке с задержкой до минуты. `force=1` — запустить как есть: недостающие коммиты не потеряются,
  они придут опоздавшими в следующий отчёт. Cron и очередь этой проверкой не блокируются никогда.
- **Снимок машины истёк** (молчала дольше 9 дней) → не 409 (push его не вернёт), а строка `warnings` в ответе 202 и в
  сноске отчёта; её коммиты не старше ~28 суток вернутся опоздавшими (более старые — известный предел, S14 в
  [07-selection](07-selection.md#сценарии)).
- **Откат через `wrangler kv key delete`** вместо маршрута: список учтённого не обновлён. Одиночный — работает; двойной
  — 409; первый же `/run` или `GET /ingest/preview` перепишет список, следующий push вылечит.
- Поддерживается только снятие **верхнего** снимка state, сколько угодно раз. Удаление из середины цепочки не
  поддерживается: даёт ложные 409.
- Две известные особенности перезапуска, проверенные чтением кода. Путь отчёта выводится из `until` в UTC
  (`src/run.ts:66-67`): при `TIMEZONE` от UTC+10 и восточнее перезапуск с `?date=` даёт файл с другой датой — старый
  не перезаписывается, появляется второй. И пока нет `history(until:)` (остаток I0), GitHub-часть перезапуска
  захватывает и коммиты, сделанные после `until` (`src/github.ts:116`).
- Если на вопрос №4 владелец ответит «без грейса», шаг «`collector push` на всех машинах» становится обязательным
  после каждого отката, а при спящей машине честный перезапуск невозможен.

## Откат деплоя и потеря KV

Четыре правила на редкий случай; уже вышедшие отчёты ни одно из них не теряет. Главное: с I0-минимума `advanceState`
переносит незнакомые поля верхнего уровня state как есть, поэтому откат деплоя на любой код **не старше
I0-минимума** ничего не стирает — `history`, `career` и журнал учтённого (`local`) едут дальше нетронутыми:
устаревшими на недели старого кода, но целыми. Стирает только код **старше I0-минимума**: он собирает state из явного
списка полей (`src/state.ts:78-100`) и незнакомые молча теряет.

1. **Откат на код не старше I0-минимума** (но старше R0 или I1). Ничего не стирается. У недель, вышедших на коде
   старше R0, нет записи недели: пропуски в `history` закрывает разборщик (`backfill-history.ts prepare --weeks`),
   `career` пересчитывает `records-rebuild`
   ([инструкция](../week-record/02-backfill-and-recovery.md#деплой-старого-кода)). Журнал учтённого цел, и его граница
   `from` на месте: локальная работа недель старого кода (не старше 28 суток) придёт опоздавшей в первый отчёт нового
   кода. Известный предел: GitHub-коммиты этих недель в журнал не записаны, и их зеркальная локальная копия
   посчиталась бы второй раз (у владельца зеркал нет — [04](04-findings.md#локальные-репозитории)).
2. **Откат на код старше I0-минимума.** Первый же прогон стирает все три поля. `history` и `career` после возврата
   нового кода восстанавливает `scripts/records-rebuild.ts`
   ([инструкция](../week-record/02-backfill-and-recovery.md#records-rebuild-история-из-архива)). Журнал учтённого не
   восстанавливается: он стартует заново с `from = since`. Двойного счёта не будет, но локальная работа недель
   старого кода в отчёт не попадёт — молча. Лечение: вернув новый код, снять эти недели откатом
   (`DELETE /state/latest`) и перезапустить каждую с `?date=` (при 409 — сначала `collector push`): откат возвращает
   state с целым журналом, а неучтённое collector пришлёт заново из git.
3. **Откат на код старше R3.** Сначала выставить `RETROSPECTIVES=false` и задеплоить, выждать час (за это
   время уйдёт отложенное сообщение `{kind:"retro"}`), потом откатывать. Не успели — придёт одно ложное
   «еженедельный отчёт не сформирован»; файлы и state не тронуты
   ([почему](../retrospectives/03-privacy-and-failures.md#откат-деплоя-при-отложенном-сообщении-в-очереди)).
4. **Потеря KV после I1.** Вместе со state пропадают журнал учтённого, список учтённого и снимки машин. Сначала
   восстановить state: `records-rebuild.ts prepare --from-scratch`
   ([инструкция](../week-record/02-backfill-and-recovery.md#потеря-kv)) — он получится без `local`. Затем
   `collector push` на машинах или подождать час: без списка collector пришлёт полное окно. Первый прогон начнёт
   журнал с `from = since` и запишет в него GitHub-коммиты недели; список учтённого Worker опубликует сам. Уже
   отчитанное второй раз не посчитается; неучтённая работа старше `since` в отчёт не попадёт. Корректирующий отчёт
   как аварийное средство после I1 не обещан.

## Корректирующий отчёт каждую пятницу — пока не вышла I1

До выхода I1 локальная работа попадает в репозиторий отчётов отдельным файлом `<REPORTS_DIR>/<день>_local.md` рядом
с основным отчётом; три таких файла (недели №6–№8) владелец уже посмотрел и одобрил.

Собирает его локальный сборщик `scripts/local-addendum.ts` — он вырастает из прототипа, которым собраны первые три
файла; в репозитории его ещё нет. Сборщик идёт через те же чистые модули из `src/`, что и Worker. Форма команды ниже —
*принятое допущение*.

1. Дождаться основного пятничного отчёта (cron — пятница 08:00 UTC). Период взять из `GET /state`: `until` последнего
   снимка — конец недели, `until` предыдущего — её начало, `reportCount` — номер (`src/state.ts:27-32`).
2. Запустить на машине, где лежат локальные репозитории (даты коммитов основного отчёта — только даты, без текста —
   сборщик берёт у GitHub сам):
   `bun --env-file=.dev.vars scripts/local-addendum.ts --since <ISO> --until <ISO> --week <N> --repos <список> --out <клон>`
3. Прочитать получившийся файл глазами и закоммитить его в репозиторий отчётов.

| Что сборщик обязан | Чего он не делает никогда |
|---|---|
| Брать только репозитории, которых нет в основном отчёте; до появления `collector/rules.ts` (C1) — по явному списку `--repos`, после — по тем же режимам `text` / `counters` / `off` | Не меняет state: ни серии недель, ни ачивок, ни счётчиков «за всё время» |
| Пропускать неделю через `applyPrivacy` и проверять приватность репозитория отчётов (после C2 — тем же `localTextGate`); не подтверждена — только цифры | Не трогает основной отчёт: файл создаётся в режиме «только создать», существующий — ошибка |
| Считать часы на общей шкале времени с коммитами основного отчёта; вычитать строки загруженных документов | Не шлёт Telegram (по умолчанию) |
| Делать один вызов модели на неделю — тот же провайдер и те же гарантии, что у боевого прогона | Не поднимает текст в KV: источник — git на машине |
| Встраивать запись недели `kind: "corrective"` (после R0; до R0 — черновая форма, R1 переведёт её в v1) | Не выходит после I1: дальше один общий отчёт |

Владелец для своего сервера выбрал режим `text` для всех репозиториев, поэтому в его корректирующих отчётах они идут
с текстом ([журнал решений](README.md#журнал-решений)). Недели до I1 на недельном мини-графике трендов занижены (корректирующие отчёты state не меняют); ретроспектива складывает оба файла как одну
неделю работы. Рецепт возврата недель через откаты state и `push --window-days` **удалён**: он переписывал старые
отчёты, заново слал Telegram и стоил вызовов модели.

## Локальная разработка

С шаблонным `wrangler.jsonc` `INGEST_TOKEN` из `.dev.vars` **молча игнорируется**: при наличии блока
`secrets.required` `wrangler dev` грузит только перечисленные в нём ключи. Запускать так:

```
wrangler dev --var INGEST_TOKEN:<dev-token>        # или: bun run dev:ingest
```

С личным конфигом, в котором блока `secrets` нет, `.dev.vars` грузится целиком — поведение двух конфигов различается.

Проверка приёмки I1: `DELETE /state/latest` (снять настоящую неделю) → `collector scan` (строка «сервер принимает
текст: да») → `push --dry-run` (текст на месте?) → `push` → `/run?date=<день из rerun>`. Шага «сначала
`GET /ingest/preview`» больше нет: приватность репозитория отчётов проверяет сам проверочный запрос. Без отката
`?date=` уже отчитанной недели даёт `since ≥ until`, и локально ничего не выберется. Через час после **следующего**
прогона текста этой недели в KV быть не должно: `wrangler kv key get 'ingest:v1:<machineId>' --binding STATE --remote`.

## Workers Free: что измерено

Проверено на Free: недельный прогон 40–110 мс процессора проходит; Cloudflare этого не гарантирует; для больших
объёмов надёжнее платный тариф.

| Факт | Значение | Откуда |
|---|---|---|
| Тариф аккаунта владельца | Workers Free: 10 мс процессора на вызов, 50 внешних запросов на вызов, KV — 100 000 чтений и по 1000 записей / удалений / `list` в сутки, очередь — 10 000 операций в сутки, логи — 200 000 событий в сутки | панель Cloudflare, сверено с документацией |
| Реальные недельные прогоны | 37 / 44 / 64 / 113 мс процессора; 12–31 с по часам; 15–26 внешних запросов; все успешны | измерено по логам боевого Worker'а |
| Расход за месяц | около 3 с процессора на ~2 тыс. запросов | панель Cloudflare |
| Почему проходит при номинале 10 мс | Cloudflare пишет о «встроенной гибкости» лимита, цифр не называет | документация; **не гарантия** |
| Разбор недели новых коммитов с текстом (70–400 КБ) | 0,5–3,4 мс; полное окно 35 дней (2,7 МБ) стоило бы 11–17 мс | замер на стенде |
| Цена грейса | разбирается до двух недель текста: ≈ 1–7 мс | оценка по тому же замеру |
| Внешние запросы после I1 | +1 — проверка приватности репозитория отчётов: 16–27 из 50 | оценка |
| Записи KV | push'и: 5 машин × 96 = 480 в сутки в худшем случае; проверочный запрос — не больше одной записи в час; прогон — до 5 | расчёт по лимитам из [10](10-wire-and-ingest.md#формат-передачи-wire-схема-v1) |
| Прогон с локальными источниками на Free | — | **не проверено**: кода нет; замер входит в приёмку I1 |

- Нарезка прогона на куски по 10 мс через очередь отклонена владельцем. Вместо этого тяжёлая работа не создаётся:
  collector присылает только неучтённое.
- Мерить процессорное время нужно в локальном движке Cloudflare (workerd через `wrangler dev`): Node и Bun
  занижают — в workerd цифры в 1,5–3 раза выше. Боевые цифры — поле `cpuTime` в логах Worker'а.
- Страховка от тихой смерти прогона на Free (I0-минимум): следующий отчёт начинается строкой «отчёт за N дней:
  прошлый прогон не состоялся».
- Суточные квоты KV на Free считаются **на аккаунт** — их исчерпание затрагивает и другие Worker'ы владельца.
