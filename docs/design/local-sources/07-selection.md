# 07. Выбор событий: ledger

Контекст и точка врезки — в [01-architecture.md](01-architecture.md).

## Состояние и алгоритм

Состояние — необязательное поле в append-only снимке (по образцу `rates?`):

```ts
AppState.local?: {
  v: 1;
  from: IsoInstant;                        // монотонная нижняя граница; старше — никогда не учитывается
  reported: Record<string /*UTC-день authoredAt*/, string[]>;
  //   локальная запись: "<repoId6>:<h(K)>:<sha10>"     GitHub-запись: "gh:<sha10>"
  covered?: [number, number][];            // I3: учтённые интервалы сессий, в минутах эпохи
}
```

- `K = authorEpochSec "." additions "." deletions`, где `authorEpochSec = floor(Date.parse(authoredAt) / 1000)`.
- `h(K)` — первые 12 hex SHA-256. Это компактность и «не читаемый глазами журнал активности в
  state», **не секретность**: значение низкоэнтропийное.
- Ledger обрезается по `from − 7д`: запас на GitHub-коммиты, чья дата автора старше даты
  коммиттера (GitHub фильтрует `history` по дате коммиттера).

```
selectLocal(L, snapshots, github, since, until):
  если since ≥ until:            → выбрано = ∅, next = L без изменений (ledger не создаётся)
  L      := L ?? { from: since, reported: {} }                  // первый прогон с фичей: без backfill
  from   := max(until − 28д, L.from)
  G      := SHA всех GitHub-коммитов этого прогона (с датой authoredDate ?? date)

  dropGithubShas := { g ∈ G : sha10(g) ∈ L.reported в любом виде — локальном или gh: }
                    // безопасно: откат state откатывает и ledger, и счёт

  C      := коммиты всех валидных снимков, где from ≤ authoredAt < min(until, receivedAt_m + 24ч)
  группы := связные компоненты отношения (одинаковый SHA) ∪ (одинаковые repo.id и K)
  группа отбрасывается целиком, если у ЛЮБОГО её члена SHA ∈ G ∪ L.reported
                                     или (repo.id, K) ∈ L.reported
  победитель: с текстом → с большей (additions + deletions) → меньший machineId
              → меньший repo.id → меньший sha

  порядок := authoredAt победителя по возрастанию (СТАРЫЕ ПЕРВЫМИ), при равенстве — sha
  лимит   := commitsPerRunPerWeek × max(1, round((until − since) / 7д))
  доля    := floor(лимит / M), M — число машин с хотя бы одной живой группой
             (машина группы = машина победителя). Каждая машина берёт до доли своих старейших
             групп; ВСЯ неиспользованная ёмкость (недобранные доли + остаток деления) раздаётся
             оставшимся группам в общем порядке
  X'      := влезшее в лимит;  отложено := не влезшее (в ledger НЕ пишется)
  late    := |{ c ∈ X' : authoredAt < since }|
  сгорело := |{ группы из валидных снимков : L.from ≤ authoredAt < from,
               и ни у одного члена SHA нет в L.reported ∪ G, и (repo.id, K) нет в L.reported }|
             // L — входящий ledger: на первом прогоне и пока from не сдвинулся — 0
  next    := { v:1, from,
               reported: prune( L.reported
                                ∪ { запись на каждую различную тройку (repo.id, K, sha) членов групп X' }
                                ∪ { "gh:"+sha10 : g ∈ G, дата ≥ from − 7д },
                                день ≥ utcDay(from − 7д) ) }
```

(«Сгорело» читать так: группа считается сгоревшей, если в этом прогоне она ушла под `from`, а ни
один её член ни разу не был учтён — ни локально, ни через GitHub.)

## Инварианты

Проверяются seeded property-тестами (без новых зависимостей) и таблицей сценариев. Горизонт машины:
`H(m) = [from, min(until, receivedAt_m + 24ч))`.

- **INV-1** — не более одного учёта на ключ вдоль любой линии снимков state.
- **INV-2** — для коммита из валидного снимка внутри `H(m)` верно хотя бы одно; статус — первое
  сработавшее в порядке: подавлен GitHub'ом → уже в ledger → отложен лимитом → учтён сейчас.
- **INV-3** — чистота: тот же state + те же снимки + тот же GitHub-набор ⇒ тот же результат.
- **INV-4** — `from` монотонен; обрезка ledger не вызывает двойного счёта в локальном выборе
  (правило отброса GitHub-коммита по SHA действует, пока запись не обрезана).
- **INV-5** — SHA, учтённый через GitHub в любом прогоне на линии state после появления
  `state.local`, локально не выбирается.
- **INV-6** — отложенный коммит либо выбирается до `authoredAt + 28д`, либо попадает в счётчик
  «сгорело» — пока он остаётся в валидном снимке. При скачке `from` больше чем на 7 дней
  (пропущенный cron) счётчик — нижняя оценка: старше окна снимка не видно.

## Проверка моделью

Спецификация дважды реализована буквально и прогнана на случайных
последовательностях (undo, `?date=`, две машины, rebase, битые снимки, зеркала, перегрузка):
первая версия дала блокер (зеркало forge → GitHub) и потери на лимите; во второй локальная часть
на ~56 тыс. прогонов держит INV-1, INV-3, INV-4, а найденные замечания (окно «сгорело», условие
запуска выбора, формулировка долей) внесены выше именно в том виде, в каком модель с ними дала
ноль нарушений INV-6. Случая, когда запись всех GitHub-коммитов в ledger подавила бы отдельный
локальный коммит, не найдено. **Эти property-тесты — обязательная часть I1**, а не документа.

## Сценарии

| Сценарий | Что происходит |
|---|---|
| Первый прогон с фичей | `from = since` → только текущая неделя, без скачка за 35 дней; сгорело = 0 |
| Ноутбук спал в момент cron | Его коммиты попадут в следующий отчёт с пометкой «опоздавшие: N» |
| Первый push машины после cron | То же: ledger уже создан пустым прогоном, неделя подключения придёт опоздавшей |
| Добавили машину / корень / хост / e-mail | До 28 дней ни разу не учтённой работы придёт как «опоздавшая» — до лимита на прогон за отчёт; не нужно — `notBefore` в конфиге |
| `DELETE /state/latest` + rerun | Снимок state откатывается вместе с ledger → та же выборка + то, что успело прийти |
| `?date=` старой недели **после** отката | Надёжно — примерно для 3 полных недель назад (окно снимка 35 дней) |
| `?date=` **без** отката (`since ≥ until`) | Локально ничего не выбирается, ledger не трогается. Но сам такой прогон и сегодня вреден: выпускает мусорный отчёт и откатывает `lastRunUntil` → I0 предлагает отвечать 409 |
| Catch-up 3–4 недели | Лимит растёт пропорционально длине; сверх него — откладывается, старые первыми |
| Устойчивая перегрузка (> лимита в неделю) | Отчёт отстаёт до 4 недель и состоит из опоздавших; сверх того — сгорает и считается. Лечится `exclude` |
| Rebase / amend без изменения статистики | Новый SHA, тот же `K` → попадание в ledger |
| Зеркало forge → GitHub, та же неделя | Локальная копия подавлена по SHA, SHA записан в ledger |
| Зеркало, локальная копия приехала неделей позже | SHA уже в ledger как `gh:` → не выбирается |
| Зеркало отстало (GitHub увидел неделей позже) | GitHub-коммит отброшен по точному SHA из ledger |
| Один репо на двух машинах, worktrees | Дедуп в прогоне по SHA/`K`, между прогонами — ledger |
| Часы машины спешат / дата из будущего | Коммит ждёт, пока `authoredAt < until`; дальше +24 ч collector его не отправляет вовсе (счётчик) |
| Push гонится с cron (KV ~60 с) | Прогон читает прошлый снимок; недостающее приедет как опоздавшее |
| Падение между `commitFile` и `saveState` | Ledger не продвинут; повтор **в тот же UTC-день** перезапишет отчёт, следующий cron — выпустит отчёт за обе недели. Между ними стоит ещё `notifyTelegram` |
| Машина исчезла | Снимок истёк по TTL, запись индекса снята прогоном, учтённые ключи остаются в ledger |
| Collector новее Worker'а | Неизвестные поля считаются в сноску; неизвестная `schema` → машина пропущена + предупреждение |
| `INGEST_TOKEN` убрали на N недель и вернули | `local` переносился, GitHub-ключи дописывались; неучтённое за 28 дней приходит как опоздавшее |
| Ротация токена | Снимки со старым `tk` отброшены и сняты; машины с новым токеном присылают окно заново |
