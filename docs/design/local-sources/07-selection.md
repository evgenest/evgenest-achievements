Контекст, точка врезки и контракт проверочного запроса — в [01-architecture.md](01-architecture.md); схема снимка, лимиты

## Главное

Один коммит учитывается один раз, что бы ни случилось — две машины, rebase, зеркало на GitHub, откат; решает это
журнал на Worker'е, а список для машин лишь экономит трафик.

- **Журнал учтённого (ledger)** — короткие хеши уже посчитанных коммитов, локальных и с GitHub. Лежит внутри state,
  поэтому откат `DELETE /state/latest` откатывает и его.
- **Список учтённого** — копия журнала в ключе KV `ingest:v1:accounted`, которую читает collector, чтобы не присылать
  уже учтённое. Это подсказка, а не источник истины.
- **Кто за что отвечает.** Журнал учтённого отвечает за «не учесть дважды», запись недели — за «к какой неделе
  отнести на графике»; это два независимых механизма. Разбивка опоздавших коммитов по неделям (`late`) считается в
  момент сборки записи из дат коммитов и `history` — [../week-record/01-schema.md](../week-record/01-schema.md).
- Честная граница: «опоздавшие» здесь — только локальные коммиты. GitHub отбирает историю по дате коммиттера
  (проверено живым запросом, [04](04-findings.md)), поэтому коммит, запушенный на GitHub с опозданием, этот механизм
  не ловит — по крайней мере до I5.

## Журнал внутри state

Журнал — необязательное поле снимка state (по образцу `rates?`); кода ещё нет, поэтому смена формата записи
перехода не требует.

```ts
AppState.local?: {
  v: 1;
  from: IsoInstant;                        // монотонная нижняя граница; старше — никогда не учитывается
  reported: Record<string /*UTC-день authoredAt*/, string[]>;
  //   локальная запись: "<sha10>:<hk12>"          GitHub-запись: "gh:<sha10>"
  covered?: [number, number][];            // I3: учтённые интервалы сессий, в минутах эпохи
}
// K    = authorEpochSec "." additions "." deletions;  authorEpochSec = floor(Date.parse(authoredAt) / 1000); числа СЫРЫЕ
// hk12 = первые 12 hex SHA-256 от (repoId — все 12 hex — + "\n" + K);  sha10 = первые 10 hex SHA коммита
```

- `hk` всегда считает **Worker** из полей коммита; присланным хешам он не доверяет.
- Почему соль. Прежняя запись `<repoId6>:<h(K)>:<sha10>` хешировала бедное значение (секунда и два числа). Теперь
  хеши публикуются в списке учтённого, и держатель утёкшего токена перебором восстановил бы посекундную ленту
  коммитов. С полным id репозитория в роли соли перебор невозможен без доступа к самому репозиторию. Открытый
  `repoId6` убран: он позволял группировать активность по проектам.
- Цена коротких хешей: ложное совпадение — коммит, который молча никогда не попадёт в отчёт. Вероятность ≈ 1e-8 на
  коммит для `sha10` и ≈ 1e-11 для `hk12` (оценка). Длины — *принятое допущение*; менять формат после первого боевого
  прогона дорого.
- Журнал обрезается по `from − 7 д`: запас на GitHub-коммиты, чья дата автора старше даты коммиттера.

## Алгоритм

Чистая функция; по сравнению с первой версией изменились формат записи и одно правило — замыкание ключей.

```
selectLocal(L, snapshots, github, since, until):
  если since ≥ until:            → выбрано = ∅, next = L без изменений (журнал не создаётся)
  L      := L ?? { from: since, reported: {} }                  // первый прогон с функцией: прошлое не поднимается
  from   := max(until − 28д, L.from)
  G      := SHA всех GitHub-коммитов этого прогона (с датой authoredDate ?? date)

  dropGithubShas := { g ∈ G : sha10(g) ∈ L.reported в любом виде — локальном или gh: }
                    // безопасно: откат state откатывает и журнал, и счёт

  C      := коммиты всех годных снимков (полных и неполных), где from ≤ authoredAt < min(until, receivedAt_m + 24ч)
  группы := связные компоненты отношения (одинаковый SHA) ∪ (одинаковый hk)
  группа УЧТЕНА, если у ЛЮБОГО её члена sha10 ∈ G ∪ L.reported или hk ∈ L.reported
         → отбрасывается целиком; ЗАМЫКАНИЕ: записи "<sha10>:<hk12>" ВСЕХ её членов идут в next
  победитель: с текстом → с большей (additions + deletions) → меньший machineId → меньший repo.id → меньший sha

  порядок := authoredAt победителя по возрастанию (СТАРЫЕ ПЕРВЫМИ), при равенстве — sha
  лимит   := commitsPerRunPerWeek × max(1, round((until − since) / 7д))
  доля    := floor(лимит / M), M — число машин с хотя бы одной живой группой (машина группы = машина победителя).
             Каждая машина берёт до доли своих старейших групп; ВСЯ неиспользованная ёмкость (недобранные доли +
             остаток деления) раздаётся оставшимся группам в общем порядке
  X'      := влезшее в лимит;  отложено := не влезшее (в журнал НЕ пишется)
  late    := |{ c ∈ X' : authoredAt < since }|
  сгорело := |{ группы из годных снимков : L.from ≤ authoredAt < from, и ни у одного члена нет ни sha10, ни hk
               в L.reported, и sha10 нет в G }|      // L — входящий журнал: пока from не сдвинулся — 0
  next    := { v:1, from,
               reported: prune( L.reported ∪ { "<sha10>:<hk12>" каждого члена групп X' } ∪ замыкание
                                ∪ { "gh:"+sha10 : g ∈ G, дата ≥ from − 7д },   день ≥ utcDay(from − 7д) ) }
```

«Сгорело» читать так: группа ушла под `from` в этом прогоне, а ни один её член ни разу не был учтён — ни локально, ни
через GitHub. Коммит без текста (см. ниже) — обычный член группы; победить он не может, потому что при полном снимке
его группа всегда учтена (INV-9).

**Замыкание ключей.** У коммита два ключа — SHA и `hk`. Если группа отброшена как учтённая, в журнал дописываются
записи всех её членов. Тогда у копии, совпавшей сначала по одному ключу, на следующем круге совпадут оба, и она
перестанет ездить. Попутно это лечит старую слабость: rebase-копия переставала ловиться, как только оригинал выпадал
из окна или стирался из git. Цена — байты в журнале. Без замыкания счёт тоже верен (в модели 0 нарушений), но коммиты
без текста ездили бы каждый час всё окно.

## Список учтённого: подсказка, а не источник истины

Список нужен только для экономии — меньше байт, меньше процессорного времени, меньше текста в KV; выбор по-прежнему
делает журнал. Форма ключа — в [01](01-architecture.md).

| Список учтённого — это | Список учтённого — это не |
|---|---|
| чистая производная журнала из state; пишет только Worker | не журнал «что я отправлял» на машине: collector берёт список заново при каждом push и ничего не помнит |
| короткие хеши всех записей журнала, включая `gh:` — иначе текст репозиториев с зеркалом на GitHub лежал бы в KV всё окно | не источник истины: пропавший, отставший или обрезанный список даёт лишние байты, но не двойной счёт — лишнее отсеет журнал |
| нижняя граница `from` и метка `through` | не секрет: его читает любой держатель `INGEST_TOKEN` ([08](08-threat-model.md)) |

- **Любое подмножество журнала безопасно.** Опасно одно направление: список **шире** журнала, с которого стартует
  прогон. Так бывает после отката, и ловит это проверка полноты (ниже).
- **Почему «один ключ → без текста», а не «не слать».** Учтённый коммит никакому правилу выбора не нужен — кроме
  случая, когда он связывает неучтённую копию с GitHub-набором. Наивное «SHA или K в списке → не слать» убирало эту
  связку: rebase-копия коммита, учтённого через GitHub, считалась второй раз. В модели — 830 незамеченных
  расхождений на 20 000 историй (633 двойных счёта и их следствия). Группировка только на стороне collector'а
  оставила 78 (оригинал на одной машине, копия на другой). Итоговое правило вместе с замыканием — 0.
- **Граница `from`.** Список публикует нижнюю границу журнала того же state, что и `through`; старше неё collector не
  шлёт. Без границы текст сгоревших коммитов ездил бы и лежал в KV ещё до 7 дней. Граница берётся именно у state
  `through`, а не у текущего: иначе счётчик «сгорело» при перезапуске до push расходится с исходным прогоном. После
  отката граница сама уезжает назад — Worker сообщает collector'у, насколько глубоко ему нужны данные. Окно в
  35 дней (`WINDOW_DAYS`, [10](10-wire-and-ingest.md#формат-передачи-wire-схема-v1)) остаётся только потолком;
  `push --window-days` и `notBefore` удалены.
- **`titlesSince`** (I3) — `lastRunUntil` того же state: заголовок сессии уходит, только если у неё есть человеческий
  промпт не раньше этой отметки. Минутные метки промптов идут за всё окно: это числа, не текст.

## Грейс: отсрочка в один прогон

Публикуется журнал того state, который был **до** последнего прогона, — поэтому текст последней отчитанной недели
остаётся в снимках до следующего прогона, а привычный откат с немедленным перезапуском работает без ожидания push.

- Collector о грейсе не знает: он лишь возвращает непрозрачную метку `through`. Политика (один прогон или ноль)
  меняется одной константой на Worker'е, без изменения формата передачи и collector'ов.
- Модель: немедленный перезапуск после отката упирается в неполный снимок в 4,2% случаев с грейсом (2 576 из 61 724
  — двойные откаты) и в 42,5% без него (26 162 из 61 572).
- Цена: отчитанный текст живёт в KV до первого push после **следующего** прогона (в модели на ровной линии — до 167 ч),
  а прогон разбирает до двух недель текста (≈ 1–7 мс вместо 0,5–3,4). После нескольких откатов подряд в KV законно
  возвращается текст более старых недель. Без грейса после каждого отката нужен `collector push`, а при спящей машине
  честный перезапуск невозможен.
- Отклонено: грейс по времени (48–72 ч) — снимок перестаёт быть чистой функцией, а откат во вторник всё равно даёт
  409; два ключа на машину — удваивает записи KV (5 машин × 96 × 2 = 960 при квоте 1000) и не атомарно.

## Полнота снимка («родословная»)

Снимок полон, если всё, что collector опустил, есть в журнале, с которого стартует прогон; проверяется это по метке
`through` и цепочке ключей state — строго, без послаблений.

```ts
isComplete(through, chainKeys, SK) ⇔ through === null || (chainKeys.includes(through) && SK !== null && through <= SK)
// through — из метаданных снимка; chainKeys — ключи state:* текущей цепочки; SK — ключ state, с которого стартует прогон
```

- Цепочка state линейна, откат снимает только верхушку (`src/state.ts:123-128`). Поэтому «метка на цепочке и не
  новее SK» в точности означает «опущенное есть в журнале».
- Строгость — находка модели: послабление «метка старше самого старого снимка — значит, предок» дало 4 тихих
  расхождения на 20 000 историй (цепочку откатили до пустой и отстроили заново). Ложная тревога строгого правила
  возможна лишь при 52 и более прогонах за 9 дней жизни снимка (`HISTORY_LIMIT`, `src/state.ts:13`).
- Ручной `/run` (только при заданном `INGEST_TOKEN`) при неполном снимке отвечает 409 с перечнем машин; `force=1`
  обходит. **Cron и очередь не блокируются никогда:** считают то, что есть, и пишут сноску. Недостающее не теряется:
  его нет в журнале, значит, следующий push его принесёт, и оно придёт опоздавшим.
- Поддерживается только снятие **верхнего** снимка state, сколько угодно раз. Удаление из середины цепочки даёт
  ложные 409 и не поддерживается. По той же причине R1 (восстановление записей прошлых недель) делается строго до
  I1-T: он добавляет в цепочку снимок, который не является прогоном. Кроме прогона, ключи `state:*` пишет только
  аварийный `records-rebuild` ([../week-record/02](../week-record/02-backfill-and-recovery.md)): после I1-T он стоит
  один цикл без грейса, а список учтённого Worker пересоберёт сам по незнакомому `basis`.
- Отклонено: отказывать push'у с устаревшей меткой прямо при приёме (лишнее чтение и петли 409 из-за кеша KV ~60 с);
  хранить метку в теле снимка (предпроверке пришлось бы разбирать тела); молча считать неполный снимок.

## Инварианты

Десять свойств, которые обязаны держаться на любых последовательностях событий. Горизонт машины:
`H(m) = [from, min(until, receivedAt_m + 24ч))`.

- **INV-1** — не более одного учёта на ключ (ни один SHA и ни один `hk`) вдоль любой линии снимков state.
- **INV-2** — для коммита из годного снимка внутри `H(m)` верно хотя бы одно; статус — первое сработавшее в порядке:
  подавлен GitHub'ом → уже в журнале → отложен лимитом → учтён сейчас.
- **INV-3** — чистота: тот же state + те же снимки + тот же GitHub-набор ⇒ тот же результат.
- **INV-4** — `from` монотонен; обрезка журнала не вызывает двойного счёта в локальном выборе.
- **INV-5** — SHA, учтённый через GitHub после появления `state.local`, локально не выбирается.
- **INV-6** — отложенный коммит либо выбирается до `authoredAt + 28д`, либо попадает в «сгорело» — пока он остаётся в
  годном снимке. При скачке `from` больше чем на 7 дней (пропущенный cron) счётчик — нижняя оценка.
- **INV-7, эквивалентность** — если проверка полноты прошла у всех машин, то выбранное, опоздавшие, отложенные и
  сгоревшие совпадают с эталоном — прежней схемой «полное окно 35 дней».
- **INV-8, нет тихой потери** — после успокоения (все машины на связи → push → прогоны, пока есть отложенные) каждый
  коммит не старше `from` учтён: прямо, по `hk` или через соседа по `hk` с учтённым SHA.
- **INV-9** — коммит без текста никогда не выбран при полном снимке.
- **INV-10, срок жизни текста** — после прогона и свежего push в снимке нет текста коммитов, учтённых раньше
  последнего прогона.

## Проверка моделью и обязательная приёмка I1-P

Передача «только неучтённое» принимается только вместе с моделью: без эталона ошибки в ней тихие.

- **Что уже сделано.** Спецификация первой версии дважды реализована буквально и прогнана на случайных
  последовательностях (~56 тыс. прогонов: откаты, `?date=`, две машины, rebase, битые снимки, зеркала, перегрузка):
  INV-1, INV-3, INV-4 держатся, замечания внесены. Для новой передачи в ходе дизайна написан прототип модели с
  эталоном: две системы идут по одной случайной истории — прежняя «полное окно» и новая. Итог: 0 нарушений на ≈ 294
  тыс. прогонов (≈ 276 тыс. сравнённых) при грейсе 1 и 0 при грейсе 0 (≈ 194 тыс.); все 21 сценарий пройдены.
  **Оговорки:** прототип лежит вне репозитория и крутит копии функций; он проверяет логику учёта, а не гонки KV по
  времени («отставшее чтение» в нём грубее реальности: 10% push'ей получают прошлую версию списка).
- **I1-P (размер S).** Модель переносится в `test/ingest/model/` так, чтобы тест крутил **настоящие** `selectLocal`,
  `buildAccounted`, `isComplete` и сборку снимка collector'а, а не их копии. Генератор случайных историй — с
  заданным зерном, без новых зависимостей. Эталон полного окна остаётся в тестах навсегда.
- **Операции в модели:** коммиты, клоны между машинами, rebase (старая копия остаётся или исчезает), зеркало на
  GitHub с задержкой, push (часть — с отставшим списком), машины вне сети, cron и ручные прогоны, одиночный и
  двойной откат с обновлением списка и без, немедленный перезапуск, ротация токена, сбой записи списка, прогоны с
  выключенной функцией, малый лимит (чтобы работало «отложено»), срок жизни снимка 9 дней.
- **Приёмка.** Не меньше 50 000 сравнённых прогонов в CI без нарушений INV-1 и INV-7…INV-10; все сценарии таблицы
  ниже с номером S (21 проверка); проверка самой проверки: наивное правило «SHA или K → не слать» и нестрогая
  родословная **обязаны ронять тест** — иначе тест ничего не ловит. Отдельно: на пути проверочного запроса и приёма
  снимка — ноль `list()`.

## Сценарии

Что происходит в типичных и неудобных случаях; в скобках — номер сценария в модели.

| Сценарий | Что происходит |
|---|---|
| Первый прогон с функцией (S1) | `from = since` → только текущая неделя, без скачка за 35 дней; сгорело = 0; список публикуется впервые |
| Ноутбук спал в момент cron (S2) | Его коммиты попадут в следующий отчёт с пометкой «опоздавшие: N»; неучтённое едет, сколько бы недель ни прошло, пока не старше `from` |
| Первый push машины после cron | То же: журнал уже создан пустым прогоном, неделя подключения придёт опоздавшей |
| Добавили машину, сервер, e-mail; перевели репозиторий из `off` | До 28 дней ни разу не учтённой работы придёт опоздавшей — в пределах лимита на прогон. Ручки «не раньше даты» больше нет |
| Откат + немедленный перезапуск (S3) | Те же снимки благодаря грейсу → та же выборка + то, что успело приехать; push не нужен |
| То же без грейса (S3′) | Снимок помечен неполным: выбрано 0 вместо 2. Без проверки полноты это была бы тихо пустая неделя |
| Двойной откат (S4) | Ручной `/run` → 409 с перечнем машин → `collector push` (или ждать до часа) → 202 |
| Откат через `wrangler kv key delete` (S5, S5′) | Список не обновлён. Одиночный — снимок полон; двойной — 409; первый же `/run` или preview перепишет список, следующий push вылечит |
| `?date=` **без** отката (`since ≥ until`) | Локально ничего не выбирается, журнал не трогается. Сам такой прогон вреден и сегодня → I0-минимум: 409 на входе, а внутри `runWeekly` — выход без записи отчёта, state и Telegram |
| Догоняющий прогон на 3–4 недели | Лимит растёт пропорционально длине; сверх него — откладывается, старые первыми |
| Отложено лимитом (S7) | В журнал не пишется → в списке нет → продолжает ехать с текстом → берётся следующим прогоном |
| Устойчивая перегрузка (больше лимита в неделю) | Отчёт отстаёт до 4 недель и состоит из опоздавших; сверх того — сгорает и считается. Лечится режимом `off` у шумного репозитория |
| Сгорело и граница (S8, S8′) | Считается в прогоне, где граница переезжает через коммит (он ещё в снимке: опубликованный `from` старше); затем перестаёт отправляться |
| Rebase / amend без изменения статистики | Новый SHA, тот же `hk` → группа учтена |
| Rebase уже учтённого (S12) | Совпал один ключ → едет без текста → замыкание дописывает второй → исчезает из снимков |
| Зеркало на GitHub, та же неделя (S9) | Локальная копия подавлена по SHA, SHA записан в журнал |
| Зеркало, локальная копия приехала позже (S10) | SHA уже в журнале как `gh:` и в списке → не отправляется или не выбирается |
| Зеркало отстало (GitHub увидел неделей позже) | GitHub-коммит отброшен по точному SHA из журнала |
| Зеркало + rebase-копия на другой машине (S11, S11′) | С итоговым правилом чисто; с наивным — двойной счёт |
| Один SHA с разной статистикой на двух машинах + rebase (S17, S17′) | Итоговое правило и замыкание склеивают и это, пока копии видны хотя бы одному снимку |
| Один репозиторий на двух машинах, worktrees | Список общий: копия учтённого со второй машины не отправляется; в пределах грейса едут обе и отсекаются журналом |
| Часы машины спешат / дата из будущего | Коммит ждёт, пока `authoredAt < until`; дальше +24 ч collector его не отправляет (счётчик) |
| Push гонится с cron (кеш KV ~60 с) | Прогон читает прошлый снимок; недостающее приедет опоздавшим. Отставший список — подмножество, безвреден |
| Между проверочным запросом и PUT прошёл прогон или откат | После прогона снимок — безвредное надмножество; после одиночного отката — полон (грейс); после двойного — поймает проверка полноты |
| Падение между `commitFile` и `saveState` | Журнал не продвинут, список прежний; повтор **в тот же UTC-день** перезапишет отчёт, следующий cron выпустит отчёт за обе недели |
| Сбой записи списка после `saveState` (S15) | Список остаётся старым — подмножество, безопасно; текст живёт в KV на один интервал между прогонами дольше. Лечится следующим прогоном или любым маршрутом владельца |
| Машина молчала дольше срока жизни снимка (S14) | Снимок истёк, запись индекса снята прогоном; вернувшаяся машина пришлёт неучтённое не старше `from` (28 суток) — оно придёт опоздавшим. Более старое collector не отправляет (`commitsBelowFloor`): в отчёт оно не попадёт и в «сгорело» не посчитается — Worker его не видел. Известный предел |
| Collector новее Worker'а | Незнакомые поля считаются в сноску; незнакомая `schema` → машина пропущена + предупреждение |
| `INGEST_TOKEN` убрали на N недель и вернули | `local` переносился, GitHub-ключи дописывались; неучтённое за 28 дней приходит опоздавшим |
| Откат деплоя на код, не знающий `local`, затем возврат нового кода | Код **не старше I0-минимума** переносит незнакомые поля state как есть: журнал цел, `from` на месте, локальная работа недель старого кода (не старше 28 суток) приходит опоздавшей. GitHub-коммиты этих недель в журнал не записаны — их зеркальная локальная копия посчиталась бы второй раз (известный предел). Код **старше I0-минимума** `local` стирает: двойного счёта нет, но журнал начинается заново с `from = since`, локальная работа недель старого кода в отчёт не попадает, и сноска об этом молчит; лечится откатом этих недель и перезапуском. Оба случая и потеря KV — в [05](05-operations.md#откат-деплоя-и-потеря-kv). В модели I1-P такой операции нет |
| Ротация токена (S13) | Снимки со старым `tk` отброшены и сняты; список от токена не зависит; машины с новым токеном присылают неучтённое |
| Подделанный `through` (S20) | Ручной `/run` получит рекомендательный 409 (обход `force=1`); cron и сама выборка не затронуты |
