## Локальные репозитории

Заметная часть работы владельца лежит там, куда Worker не достанет, а дубли от rebase и worktree обычны: нужен локальный
сборщик и отсев дублей не только по SHA.

| Факт | Значение | Следствие |
|---|---|---|
| Репозитории, которых Worker не видит | несколько из ~30: свой git-сервер, недоступный из интернета, и репозитории без remote | Нужен локальный collector |
| Репозитории на своём сервере | 0 merge-коммитов, 0 коммитов «коммиттер ≠ автор»; ни одно имя и ни один корневой коммит не совпадают с GitHub-репозиториями | Слияние через веб-интерфейс и зеркала на GitHub у владельца **не используются**; защита от зеркал нужна другим пользователям |
| Рабочих машин | Одна | Несколько машин — для других пользователей; в тестах обязательны, в приоритетах владельца — нет |
| GitHub-клоны, которых нет в `/user/repos` | около трети GitHub-клонов; своих коммитов в них за 35 дней — 0 | Отдельный класс для чужих GitHub-клонов не нужен: до I5 пропускаются все репозитории с GitHub-remote |
| Обход домашней папки с отсечением | ~0,25 с, ~30 репозиториев | Кэш найденных репозиториев не нужен |
| Все ветки против ветки по умолчанию (один репозиторий) | 56 против 32 коммитов | Только ветка по умолчанию прячет работу в процессе |
| Строк (sha, папка) за 7 дней | ~200 на ~100 разных SHA | Worktree дублируют коммиты → схлопывание и отсев по SHA |
| Переписанные коммиты (rebase, amend) | ~17% за 7 дней; ~9% за 36 дней | Отсева только по SHA недостаточно |
| Ключ «секунда автора», 36 дней | 261 SHA → 239 ключей; 14 из схлопнутых — **разные последовательные коммиты** одной секунды (5,4%) | Ключ отвергнут |
| Ключ «секунда + additions + deletions» | 253 = 261 − 8 rebase-копий; ни одной пары с одинаковой статистикой | Принят как `K` |
| Статистика GitHub против `git log --shortstat -M` | Совпала на 42 из 42 коммитов (без переименований) | Между источниками сравнение идёт только по SHA; `K` с GitHub не сопоставляется |
| Размер текста коммитов | ~1,4 КБ на коммит (кириллица — 2 байта на символ); неделя ≈ 150 КБ | 2000 коммитов с текстом ≈ 2,7 МиБ > лимита 2 МиБ → нужно сжатие по размеру ([03](03-collector.md#порядок-push)) |
| Один код под Bun и как `bun build --compile` | Работает, если ядро на `node:*` + `fetch`; бинарник — 60–86 МБ на ОС ради ~10 КБ программы | Отдельные скрипты под ОС не нужны; бинарники отложены |

## Строки: PDF и письма git считает текстом

Число строк бывает бессмысленным; часы от этого не страдают — **измерено** на одной из недель.

| Факт | Значение | Следствие |
|---|---|---|
| Добавленные строки по неделям | Одна из недель дала на порядок больше строк, чем соседние: сотни тысяч против ~10 тыс. | Это не работа в десятки раз больше обычной, а загрузка документов |
| Откуда эти строки | git считает текстом PDF и письма; такие файлы дают сотни тысяч «строк» — почти всё превышение | git считает файл текстом, если в его начале нет нулевых байтов, — у части PDF и у писем их нет |
| Часы той же недели | не искажены: у оценки есть потолок на коммит | Правило нужно только для строк |

Отсюда два правила: для локальных коммитов collector отделяет строки загруженных документов по расширениям файлов
([03a-git-calls.md](03a-git-calls.md#строки-загруженных-документов)); для GitHub-коммитов, где списка файлов нет, —
порог массового коммита 10 000 строк ([../week-record/01-schema.md](../week-record/01-schema.md), пункт №9).

## Зачем переключатель на репозиторий

Модель пересказывает текст коммитов любого репозитория одинаково подробно — **проверено** на корректирующих отчётах;
поэтому «с текстом или без» решается по каждому репозиторию, а не одной общей ручкой.

- Общая ручка «текст для всех» первым же прогоном отправила бы текст всех репозиториев сервера провайдеру модели, в
  Telegram и в историю git — в том числе тех, которые пользователь показывать не собирался. Отсюда три режима: с
  описанием / только цифры / не собирать.
- Владелец для своего сервера выбрал режим `text` для всех репозиториев
  ([журнал решений](README.md#журнал-решений)). Переключатель остаётся для других пользователей, значение по умолчанию —
  цифры.

## Скан идентификаторов (имена, контакты, домены)

Личных идентификаторов в тексте мало, почти все люди в нём — публичные лица, а главный идентификатор сидит не в тексте,
а в именах репозиториев и доменов — **измерено**; отсюда рекомендация словарь замен сейчас не строить (пункт №1).

| Что | Значение |
|---|---|
| Проверено текстов | около 3,5 тыс.: заголовки и тела коммитов, PR, issues, заголовки сессий |
| Тексты хотя бы с одной находкой | около 11%; с записью из чернового словаря — около 6% |
| Заголовки коммитов с находкой | около 8%; с записью словаря — около 4% |
| Доля знаков, задетых находками, в тексте, который видит модель | около 1% |
| Черновой словарь | около ста записей, большинство — имена людей |
| Кто эти люди | примерно девять из десяти — публичные лица, чьи имена и так опубликованы |
| Где сосредоточены находки | в небольшой части проектов |
| Цена словаря на Worker'е | 6–11 мс процессора на проход при ~120 записях; наивная реализация — 13–26 мс (замер в Node; в workerd дороже) |

## git: проверено на тестовых репозиториях (git 2.47)

Любой разделитель, кроме NUL, подделывается, а неполный клон способен исполнить чужой код при простом `git log`; защита
описана в [03a-git-calls.md](03a-git-calls.md#вызовы-git).

| Факт | Следствие |
|---|---|
| Байты `\x1e`/`\x1f`/`\x1d` проходят в `%b` и `%ae` без экранирования: тело коммита подделывает и строку статистики, и целые записи; e-mail автора делает то же в режиме без текста | Только NUL (`-z`, `%x00`): git отвергает NUL в сообщении |
| `--author` — поиск подстроки; несколько `--author` объединяются по ИЛИ | Точная перепроверка e-mail в JS |
| Неполный клон (partial clone) с враждебным remote исполняет код при `git log --shortstat` (`ext::`, `core.sshCommand`, `uploadpack`, даже без remote через `extensions.partialClone`); обычный клон `--filter=blob:none` молча ходит в сеть | `GIT_NO_LAZY_FETCH=1` (≥ 2.45) + пропуск неполных клонов. Один `-c protocol.allow=never` не спасает |
| Закрепления `core.fsmonitor=false`, `--no-textconv` работают (без них код исполняется в `git status` / `git log -p`) | Оставляем |
| `--since` останавливает обход на первом старом (по дате коммиттера) коммите и теряет лежащие под ним коммиты окна | `--since-as-filter` |
| `-c diff.algorithm=myers` — лишь запасной алгоритм: драйвер из атрибутов дал 20/20 против 13/13 при `--diff-algorithm=myers`; атрибут `binary` и `core.bigFileThreshold` обнуляют счётчики | Флаг командной строки + закрепление порога; остаточная зависимость от атрибутов — ограничение `K` |
| Корень «от HEAD» различается у клонов с разной выбранной веткой; у клона с обрезанной историей «корень» — граница, и она меняется при углублении | Корень по `HEAD --branches --remotes`; у обрезанного клона id — из пути remote, а правило `text` не даётся |
| `config --get remote.origin.url` возвращает алиас `insteadOf`, `remote get-url` — настоящий адрес | Хосты определяются только через `get-url --all` |
| `rev-parse --git-common-dir` для основного worktree возвращает относительный `.git` | `--path-format=absolute` |
| `--all` показывает внутренности stash; `HEAD --branches --remotes` — нет | Никогда `--all` |
| `git log -z --shortstat` не печатает статистику для пустого коммита; блок статистики коммита N приклеен к началу записи N+1 | «Не более одной строки статистики»; разбор по реальной раскладке |
| Тело запроса кусками, без `Content-Length`, размерный барьер приёма не обходит | Порядок проверок в обработчике достаточен |
| Токен отчётов (право на содержимое) читает поля `private` и `visibility` репозитория | Проверка приватности репозитория отчётов не требует нового токена |
| GitHub GraphQL `history(since/until)` фильтрует по дате **коммиттера** (живой запрос) | Локальное окно — по дате автора; на стыке источников полагаемся на SHA и журнал учтённого |

## Видимость: проверено живыми запросами

Проверка «коммит существует в репозитории» на GitHub подделывается через чужой форк; правило и выводы — в
[09-public-visibility.md](09-public-visibility.md).

| Факт | Следствие |
|---|---|
| `repository.object(oid)` находит коммит, которого в репозитории нет: он лежит в чужом форке (сеть форков общая), а `author.user.login` подделывается e-mail'ом автора | Одной этой проверки мало |
| `compare(headRef: <sha>)` от ветки по умолчанию: для поддельного коммита `DIVERGED`, `aheadBy = 2`; для настоящего `BEHIND`, `aheadBy = 0` | Условие `aheadBy === 0` доказывает достижимость |
| 300 сравнений + 300 объектов с текстом и статистикой | 1 запрос, 1 единица лимита GraphQL, ~180 КБ, ~10 с |
| Сортировка веток `TAG_COMMIT_DATE` по свежести не сортирует: у репозитория с 254 ветками первые 20 — старые | Перечисление веток отклонено |
| Анонимные списки коммитов: Forgejo — 50 на страницу, ветка по умолчанию, ~158 КБ; GitLab — `all=true&since`, 100 на страницу, ~126 КБ; на приватное и несуществующее — 404 | Основа необязательной I6 |
| В опубликованном описании API Forgejo у `/commits` нет фильтров по дате и автору; до приватного сервера Worker не достучится | Чтение API сервера из Worker'а как основной путь отклонено |

## Кодовая база

Весь конвейер после приватности выводится из одной недели, поэтому точка врезки одна; но в работающем коде нашлись
места, которые нужно поправить до любых новых функций (S0, I0-минимум) — **проверено чтением кода**.

| Факт | Где | Следствие |
|---|---|---|
| Весь конвейер после приватности выводится из одного `WeekActivity` | `src/run.ts:40-41` | Одна точка врезки |
| Лог ошибки модели пишет причину целиком, а AI SDK вкладывает в неё весь сырой ответ модели | `src/llm.ts:214` | **S0(а):** в сохранённые логи попадает содержимое отчёта, хотя `SECURITY.md` обещает «только форму» |
| В шаблонах включено сохранение трасс | `wrangler.jsonc:22-26`, то же в ci-шаблоне | **S0(б):** трассы пишут полные адреса запросов, ключи и метаданные KV — [08](08-threat-model.md) |
| Репозиторий отчётов сам считается проектом недели: коммит робота `report: week of …` есть во всех файлах отчётов (включая файл-дубль недели №7, оставшийся от отменённого прогона) | `src/run.ts:68`, сбор в `src/github.ts:196` | I0-минимум: исключить `REPORTS_REPO` из сбора — иначе коммиты ретроспектив станут «работой» с часами |
| PR и issues отбираются по `updated:>=<день>`: один PR попадает в несколько недель | `src/github.ts:201-202` | Месячные суммы были бы завышены → событийные счётчики в R0 |
| Потребитель очереди не проверяет форму сообщения; `max_concurrency` в конфигах нет | `src/index.ts:49-53`, `wrangler.jsonc` | Сначала разбор `kind`, потом ретроспективы; `max_concurrency: 1` — в I0-минимум |
| `advanceState` собирает state из явного списка полей | `src/state.ts:78-100` | Деплой более старого кода молча стирает незнакомые поля (`history`, `career`, позже `local`) → I0-минимум: незнакомые поля верхнего уровня переносятся как есть |
| `{...state.allTime}` и `{...state.lastWeek}` уходят в данные для модели под плоским списком разрешённых ключей | `src/sanitize.ts:167-168` | Любое новое поле в этих объектах роняет защиту на **следующем** прогоне у всех форков → остаток I0 |
| `redactPrivate` копирует объекты целиком | `src/privacy.ts` | Сегодня не утечка, а мина → остаток I0: явные списки; необязательный `authoredDate` обязан сохраниться — от него зависят часы |
| Имя репозитория, похожее на hex-строку, роняет прогон через `findSecret` | `src/secrets.ts`, `src/sanitize.ts` | Имя из снимка проверяется и заменяется на `local/<id>` |

| `?date=` без отката state даёт `since ≥ until` | `src/run.ts:36-38` | I0-минимум: 409 на входе и защита внутри `runWeekly` (cron и очередь идут мимо HTTP-обработчика); запись недели при этом не создаётся |

## Cloudflare: что измерено на боевом аккаунте

Тариф владельца — Workers Free, и недельный прогон на нём проходит; это наблюдение, а не гарантия Cloudflare.

| Факт | Значение | Откуда |
|---|---|---|
| Тариф | **Workers Free** — подтверждено; 10 мс процессора на вызов, 50 внешних запросов на вызов (и отдельно 1000 обращений к сервисам Cloudflare), KV — 100 000 чтений и по 1000 записей / удалений / `list` в сутки **на аккаунт**, очередь — 10 000 операций в сутки, логи и трассы — 200 000 событий в сутки | панель Cloudflare, сверено с документацией |
| Реальные недельные прогоны | **37 / 44 / 64 / 113 мс** процессора; **12–31 с** по часам; **15–26** внешних запросов; все завершились успешно | измерено по логам боевого Worker'а |
| Расход за месяц | около 3 с процессора на ~2 тыс. запросов | панель Cloudflare |
| Платный тариф, для сравнения | 30 с процессора на вызов по умолчанию (до 5 мин), cron с интервалом от часа — до 15 мин | документация |
| Почему проходит при лимите 10 мс | Лимит — номинал: документация обещает «встроенную гибкость» для редких превышений, но **величину допуска не называет** | документация; не гарантия |
| Где мерить процессорное время | В локальном движке Cloudflare (workerd через `wrangler dev`). Node и Bun **занижают: в workerd цифры в 1,5–3 раза выше** на тех же данных | измерено на стенде |
| Сколько хранится история | Метрики Worker'а — 3 месяца; логи и трассы — 3 дня на Free, 7 на платном | документация |
| Разбор недели новых коммитов с текстом (70–400 КБ) | 0,5–3,4 мс; полное окно 35 дней (2,7 МБ) — 11–17 мс; рукописный валидатор в ~10 раз дешевле zod | стенд (Node; в workerd дороже) |
| Теоретический максимум внешних запросов нынешнего прогона | ~56 при лимите 50 (5 страниц репозиториев, 20 проверок видимости, CI и деплои по репозиториям) | оценка по коду |
| KV | Значение ≤ 25 МиБ, метаданные ≤ 1024 байта, 1 запись в секунду в один ключ, срок жизни ≥ 60 с; чтения кешируются до ~60 с, **включая ответ «ключа нет»**; отдельного чтения метаданных нет (`getWithMetadata` + `cancel()`) | документация |
| Очередь | Сообщение ≤ 128 КБ и живёт 24 ч; по умолчанию 3 повтора | документация |
| `wrangler kv key …` | По умолчанию работает с **локальным** хранилищем; нужен `--remote` | проверено |
| Прогон с локальными источниками на Free | — | **не проверено:** кода нет; замер в workerd входит в приёмку I1 |

Нарезку прогона на куски по 10 мс через очередь владелец отклонил; вместо неё тяжёлая работа не создаётся — collector
присылает только неучтённое. В модели передачи наивное правило дало 830 незамеченных расхождений на 20 000 историй,
итоговое — 0; немедленный перезапуск после отката упирается в неполный снимок в 4,2% случаев с грейсом и в 42,5% без
него ([07-selection.md](07-selection.md)).

## Сессии Claude Code

Время по сессиям — отдельная содержательная метрика, но не слагаемое часов; формат файлов внутренний, поэтому читатель
обязан быть терпимым. Профиль: ~100 основных сессий, ~32 тыс. записей, 22 версии программы, 0 ошибок разбора.

| Факт | Следствие |
|---|---|
| Формат официально внутренний; хранение по умолчанию 30 дней; `CLAUDE_CONFIG_DIR` — один каталог | Источник необязательный; нужен локальный кэш отметок: свежий обход не видит удалённого |
| `origin.kind == "human"` надёжен там, где есть; ~15% файлов (включая свежие версии) без `origin` вовсе | Такие файлы пропускаются и считаются; метрика слегка занижает |
| За 7 дней: ~30 сессий, ~230 человеческих промптов; у всех есть `aiTitle` (медиана 27 символов, максимум 57) | Заголовки — ~1 КБ в неделю |
| Рабочая папка → корень репозитория определяется для 228 из 229 промптов; **45% промптов — в репозиториях вне GitHub** | Привязка к проекту осуществима и ценна |
| Каждый блок ответа — отдельная запись с повтором `usage`; `turn_duration` бывает больше длительности сессии | Токены и стоимость не берём; «время» — только от отметок человеческих промптов |
| Все коммиты недели лежат внутри интервалов сессий; ~4 ч из ~27 ч сессий — без коммита в пределах 30 мин | Отдельная метрика; «сессии без коммитов» — содержательная строка |
| Метрика по принятому определению — ~16 ч за неделю; пауза после «хвоста» — ~17 ч; без склейки интервалов — ~12 ч | Определение — в одном месте, на Worker'е; принято владельцем |
| Хук `SessionEnd` — таймаут 1,5 с; `/branch` и `--fork-session` копируют запись сессии | Хуки как способ сбора отклонены; дубли снимаются по `uuid` |

Аналоги, у которых взяты приёмы: git-standup, mgitstatus, gita, ghq (обход корней, фильтр по автору); WakaTime,
Wakapi, ActivityWatch (маленький агент → сервер); git-hours (часы по промежуткам — уже в `src/hours.ts`); ccusage,
agentsview, claude-code-log, vibe-log (терпимый разбор JSONL, отсев по id).

## Известные ограничения дизайна

Почти все они дают лишний или опоздавший счёт, видимый в сноске; молча работа теряется только в четырёх случаях, и
все они названы ниже.

- **Неделя доставки, а не работы.** Серия недель и ачивки считаются по неделе, в которую коммит приехал: опоздавшая
  работа обнулит серию, а следующая неделя станет «активной» за её счёт. Короткий срок жизни снимка (9 дней) это
  усиливает: машина, молчавшая дольше, привезёт неучтённое (не старше 28 суток) «опоздавшим». На графике трендов это поправляет поле `late`.
- Переписывание **с изменением статистики** (amend, rebase с конфликтами) считается дважды, пока старая копия видна.
- Rebase-копия **между источниками** (зеркало своего сервера → GitHub) и копии с разной статистикой на двух машинах
  больше не задваиваются: правило «один ключ → без текста» и замыкание ключей закрывают оба случая, пока копии видны
  хотя бы одному снимку ([07](07-selection.md)).
- Один репозиторий с разными `id` на двух машинах: точный SHA склеивается, rebase-копии — нет.
- Слияние со сжатием (squash) в веб-интерфейсе сервера: строки посчитаются дважды (часы — нет: шкала одна).
- Молчаливая потеря, два крайне редких случая: два разных коммита одной секунды с одинаковой статистикой в одном
  репозитории схлопнутся (0 случаев из 261); совпадение коротких хешей списка учтённого (≈ 1e-8 на коммит, **оценка**).
- Молчаливая потеря, два названных предела: работа машины, молчавшей дольше ~28 суток, после пробуждения в отчёт не
  попадает и счётчиком не видна — collector её не отправляет (`commitsBelowFloor`), нового механизма не вводим
  ([07](07-selection.md#сценарии), S14); локальная работа недель, вышедших на коде старше I0-минимума, — лечится
  откатом этих недель ([05](05-operations.md#откат-деплоя-и-потеря-kv)).
- Опоздавшие коммиты получают на шкале часов «окно начала сессии» (120 мин) — ограниченное завышение.
- Отложенное лимитом и не выбранное за 28 дней сгорает и показывается счётчиком; при устойчивой перегрузке отчёт
  отстаёт до 4 недель. Шумный репозиторий лечится режимом `off`.
- Коммит, учтённый «цифрами», описание задним числом не получит; публичные коммиты в неслитых ветках показываются
  приватными ([09](09-public-visibility.md)); корректирующие отчёты на недельный график трендов не попадают.
- Приватность Telegram-чата Worker не проверяет; вышедшие отчёты не отзываются, если репозиторий отчётов открыть.
- PR и issues со своего сервера не собираются; `language: null` у локальных репозиториев → «—» в таблице.
- Репозитории без remote с общей историей (форк, шаблон) делят один `id`.
- GitHub-сторона: только `/user/repos`, ветка по умолчанию, до 100 коммитов на репозиторий — до I5 остальное не видно.
