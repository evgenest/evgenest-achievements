# 04. Замеры и факты

Основание решений из журнала в [README.md](README.md). Замеры сделаны 2026-09-18 на машине автора,
только по метаданным: текст коммитов и сессий не читался и не выводился. Часть чисел округлена.

## Локальные репозитории

| Факт | Значение | Следствие |
|---|---|---|
| Репозитории, которых Worker не видит | 5 из ~30: forge, недоступный из интернета, и репозитории без remote | Нужен локальный collector |
| Forge-only репозиторий за неделю | ~50 коммитов, ~15 тыс. строк | Это и есть потерянная работа |
| Forge-репозитории автора | 0 merge-коммитов, 0 коммитов «коммиттер ≠ автор»; ни одно имя и ни один корневой коммит не совпадают с GitHub-репозиториями | Squash-merge в веб-интерфейсе и зеркала на GitHub у автора **не используются**; защита от зеркал нужна другим пользователям |
| Рабочих машин | Одна | Multi-machine — для других пользователей; в тестах обязателен, в приоритетах автора — нет |
| GitHub-клоны, которых нет в `/user/repos` | 9 из 25; своих коммитов в них за 35 дней — 0 | Класс `github-foreign` автору не нужен → I2 |
| Обход домашней папки с отсечением | ~0.25 с, 34 репозитория | Кэш найденных репозиториев не нужен |
| Все ветки vs ветка по умолчанию (один репо) | 56 против 32 коммитов | Только default-ветка прячет работу в процессе |
| Строк (sha, папка) за 7 дней | ~200 на ~100 разных SHA | Worktree дублируют коммиты → схлопывание + дедуп по SHA |
| Переписанные коммиты (rebase/amend) | ~17% за 7 дней; ~9% за 36 дней | Дедуп только по SHA недостаточен |
| Ключ «секунда автора», 36 дней | 261 SHA → 239 ключей; 14 из схлопнутых — **разные последовательные коммиты** одной секунды (5.4%) | Ключ отвергнут |
| Ключ «секунда + additions + deletions» | 253 = 261 − 8 rebase-копий; ни одной пары с одинаковой статистикой | Принят как `K` |
| Статистика GitHub vs `git log --shortstat -M` | Совпала на 42 из 42 коммитов (без переименований) | Между источниками сравнение идёт только по SHA; `K` с GitHub не сопоставляется — совпадение статистики на rename не доказано |
| Размер текста коммитов | ~1.4 KB на коммит (кириллица — 2 байта на символ); неделя ≈ 150 KB | 2000 коммитов с текстом ≈ 2.7 MiB > лимита 2 MiB → нужна деградация по размеру |
| Один код под Bun и как `bun build --compile` | Работает, если ядро на `node:*` + `fetch` | Отдельные скрипты под ОС не нужны. Под чистым Node 24 репо не запускается (импорты без расширений) |
| `bunx github:<owner>/<repo>` | Не документировано | Не предлагаем |
| Скомпилированный бинарник | 60–86 MB на ОС ради ~10 KB программы + подпись на macOS/Windows | Отложено |

## git: проверено фикстурами (git 2.47)

| Факт | Следствие |
|---|---|
| Байты `\x1e`/`\x1f`/`\x1d` проходят в `%b` и `%ae` без экранирования: тело коммита подделывает и строку shortstat, и целые записи; e-mail автора делает то же в режиме без текста | Только NUL (`-z`, `%x00`): git отвергает NUL в сообщении |
| `--author` — поиск подстроки; несколько `--author` объединяются по ИЛИ | Точная перепроверка e-mail в JS |
| Partial clone + враждебный promisor remote исполняет код при `git log --shortstat` (`ext::`, `core.sshCommand`, `uploadpack`, даже без remote через `extensions.partialClone`); обычный `--filter=blob:none` клон молча ходит в сеть | `GIT_NO_LAZY_FETCH=1` (≥ 2.45) + пропуск partial-clone. `-c protocol.allow=never` один не спасает — локальный `protocol.ext.allow=always` его перекрывает |
| Закрепления `core.fsmonitor=false`, `--no-textconv` работают (контроль: без них код исполняется в `git status` / `git log -p`) | Оставляем |
| `--since` останавливает обход на первом старом (по дате коммиттера) коммите и теряет лежащие под ним коммиты окна | `--since-as-filter` |
| `-c diff.algorithm=myers` — лишь запасной алгоритм: драйвер из атрибутов дал 20/20 против 13/13 при `--diff-algorithm=myers`; атрибут `binary` и `core.bigFileThreshold` обнуляют счётчики | Флаг командной строки + закрепление порога; остаточная зависимость от атрибутов — ограничение `K` |
| Корень «от HEAD» различается у клонов с разной выбранной веткой; у shallow-клона «корень» — граница, и она меняется при углублении | Корень по `HEAD --branches --remotes`; shallow — id из пути remote |
| `config --get remote.origin.url` возвращает `insteadOf`-алиас, `remote get-url` — настоящий URL | Классификация хостов только через `get-url --all` |
| `rev-parse --git-common-dir` для основного worktree возвращает относительный `.git` | `--path-format=absolute` |
| `--all` показывает внутренности stash; `HEAD --branches --remotes` — нет | Никогда `--all` |
| `git log -z --shortstat` не печатает строку статистики для пустого коммита; блок статистики коммита N приклеен к началу токена `%H` коммита N+1 | «Не более одной строки shortstat»; разбор по реальной раскладке |
| Chunked-тело без `Content-Length` размерный барьер ingest не обходит | Порядок проверок в обработчике достаточен |
| Токен отчётов (fine-grained, contents) читает поле `private`/`visibility` репозитория | Проверка приватности reports-репо не требует нового токена |
| GitHub GraphQL `history(since/until)` фильтрует по дате **коммиттера** (проверено живым запросом) | Локальное окно — по дате автора; на стыке источников полагаемся на SHA и ledger |

## Известные ограничения дизайна

- **Неделя доставки, а не работы.** Streak и ачивки считаются по неделе, в которую коммит
  приехал: неделя, чья работа приехала с опозданием, обнулит streak, а следующая станет
  «активной» за счёт опоздавших.
- Переписывание **с изменением статистики** (amend, rebase с конфликтами) считается дважды, пока
  старая копия видна через remote-tracking ref или на другой машине — в том числе внутри одного прогона.
- Rebase-копия **между источниками** (зеркало forge → GitHub, позже I5) считается дважды в любом
  порядке, включая один прогон: с GitHub сопоставляется только точный SHA.
- Один репозиторий с разными `id` на двух машинах (разные формы или хосты remote, ssh-алиас,
  копия без remote): точный SHA склеивается, rebase-копии — нет.
- Squash-merge в веб-интерфейсе forge: строки посчитаются дважды (часы — нет: шкала одна).
- Одна и та же правка в N репозиториях одной секундой различается (`K` — в пределах репо); два
  разных коммита одной секунды с одинаковой статистикой в одном репо схлопнутся (0 из 261).
- `K` зависит от `.gitattributes` и версии git: копии с разной статистикой на двух машинах не
  склеятся по `K` (по SHA — склеятся).
- Опоздавшие коммиты получают на шкале часов «окно начала сессии» (120 мин) — ограниченное завышение.
- Отложенное лимитом и не выбранное за 28 дней сгорает — и показывается счётчиком. При пропуске
  cron (скачок границы больше 7 дней) счётчик — нижняя оценка.
- При устойчивой перегрузке (больше лимита в неделю) отчёт отстаёт до 4 недель и целиком состоит
  из опоздавших; доля делится между машинами, но не между репозиториями одной машины — шумный
  репозиторий (авто-коммиты заметок) лечится `exclude`.
- Приватность Telegram-чата Worker не проверяет; текст, уже лежащий в KV, и закоммиченные отчёты
  не отзываются, если reports-репозиторий позже открыть.
- PR и issues с forge не собираются: разделы PR/issues и ачивка `shipper` остаются GitHub-only.
  `language: null` у локальных репо → «—» в таблице, `polyglot` их не видит.
- Репозитории без remote с общей историей (форк, шаблон) делят один `id`.
- GitHub-сторона: только `/user/repos`, первые `MAX_REPOS`, ветка по умолчанию, до 100 коммитов на
  репо. В I1–I4 всё, что сверх этого в GitHub-репозиториях, по-прежнему не видно (I5).
