>

>
> **Что просто к сведению:** всё остальное — как ретроспектива запускается, что читает, сколько стоит и
> что бывает при сбоях.

Статус: **дизайн, код не написан**. Дата: 2026-09-19. Итерации **R3** (месяц) и **R4** (год); стоят на
записи недели ([../week-record/](../week-record/README.md)), в общем порядке R3 идёт после локальных

## Главное за минуту

Раз в месяц и раз в год в репозитории отчётов появляется ещё один файл — взгляд на месяц или год
целиком; он собирается из уже готовых отчётов отдельным запуском и недельному отчёту помешать не может.

- **Что внутри.** Неделя отвечает на вопрос «что я сделал», месяц — «что изменилось благодаря мне». Все
  числа считает код, текст пишет модель по уже написанным недельным отчётам. Коммиты и GitHub
  ретроспектива не читает никогда. Макеты — в [01-reader.md](01-reader.md).
- **Одна переменная** `RETROSPECTIVES`, по умолчанию `false`: у чужого форка ничего не появляется.
- **Запуск.** Через час после каждого успешного недельного прогона в уже существующую очередь кладётся
  сообщение; отдельный запуск сам решает, какой период пора собрать. Нового cron нет.
- **Повтор ничего не тратит.** В файле лежит отпечаток входов — список недель, из которых он собран.
  Входы те же — ни вызова модели, ни сообщения.
- **Две недели-файла** (основной отчёт и корректирующий) показываются одной неделей работы.
- **Сбой:** файл не пишется, в Telegram — короткое уведомление без текста ошибки, повтор — следующей
  пятницей. Подробно — в [03-privacy-and-failures.md](03-privacy-and-failures.md).
- **Цена:** 13 вызовов модели в год сверх 52 недельных, каждый — примерно с недельный (оценка по замеру
  готовых отчётов, на живом прогоне не проверено).
- **Жёсткая дата:** первая годовая ретроспектива — за 2026 год — должна прийти в пятницу 1 января 2027.

## Что такое месячная и годовая ретроспектива

Месяц собирается из недель, год — из месяцев; на каждом уровне числа берутся из машинных записей, а
модель видит только уже написанный текст уровня ниже.

| | Месяц | Год |
|---|---|---|
| Из чего | записи недель из `history` + тексты 4–5 недельных отчётов и их корректирующих | записи и тексты до 12 месячных файлов |
| Какие недели входят | те, чей отчёт датирован этим месяцем | недели всех месяцев года |
| Числа | сумма недель | сумма месяцев |
| Текст модели | заголовок, «месяц в двух абзацах», главное, линии проектов, «что месяц говорит о тебе» | заголовок, «год в двух абзацах», большие линии года, «что год говорит о тебе» |
| Строит код | цифры, «куда ушло время», ачивки, «из чего собрано» | цифры, хроника из заголовков месяцев, проекты года, рекорды |
| Когда приходит | в первую пятницу следующего месяца, через час после недельного отчёта | в первую пятницу января, следом за декабрём |
| Вызовов модели | 1 (2 — с запасным путём) | 1 (2 — с запасным путём) |

`history` — рабочая копия записей последних 53 недель внутри state (счётчики проекта в KV, хранилище
«ключ — значение» Cloudflare); её ведёт R0. Год недельные отчёты не читает: 52 файла — это больше 50
разрешённых запросов и сотни тысяч знаков на вход модели.

## Одна переменная: `RETROSPECTIVES`

Ретроспективы стоят денег (вызов модели) и шлют сообщения, поэтому включаются явно (принцип P6 из
[общего README](../README.md)); всё бесплатное и невидимое работает без переменной.

| | `RETROSPECTIVES` не задана или `false` | `RETROSPECTIVES=true` |
|---|---|---|
| Сообщение в очередь после недельного прогона | не ставится | ставится, задержка 1 час |
| Маршрут `POST /retro` | 404, как любой неизвестный адрес | работает под `RUN_SECRET` |
| Сообщение `kind: "retro"`, оказавшееся в очереди | подтверждается без работы | обрабатывается |
| Новые файлы, вызовы модели, сообщения | нет | `monthly/`, `yearly/`, 13 вызовов в год |

Запись недели и `history` пишутся всегда (это R0) — иначе форк, включивший ретроспективы через полгода,
остался бы без прошлого. В коде это одно поле `Config.retrospectives`, читается существующей функцией
`bool()` (`src/config.ts:52`, `80-102`); переменная добавляется в шаблон `wrangler.jsonc` и в таблицу
README проекта. Новых секретов нет: хватает токена отчётов `GITHUB_REPORTS_TOKEN`.

## Как запускается: сообщение в существующую очередь

После каждого успешного недельного прогона Worker кладёт в `RUN_QUEUE` сообщение `{ kind: "retro" }` с
задержкой в час; что именно собирать, решает уже получатель — по state в момент своего запуска.

```ts
type QueueMessage =
  | { until: string }                                                     // недельный прогон — как сейчас
  | { kind: "retro"; period?: string; force?: boolean; built?: string[] };
// period и force приходят только с ручного маршрута; built — периоды, уже собранные в этой цепочке сообщений
```

1. **Где ставится.** В `runInBackground` (`src/index.ts:29-41`), сразу после успешного `runWeekly`: через
   эту функцию идут обе дороги — cron (`src/index.ts:44-46`) и ручной `/run` через очередь
   (`src/index.ts:49-53`). Вызов `RUN_QUEUE.send({ kind: "retro" }, { delaySeconds: 3600 })` стоит в своём
   `try/catch`: ошибка → строка лога `retro_enqueue_failed`, неделя уже выпущена.
2. **Сообщение без `kind`** — недельный прогон, как сегодня. Сообщение с незнакомым `kind` подтверждается
   (ack — «больше не доставлять») со строкой лога.
3. **Получатель** — потребитель очереди (queue consumer): функция Worker'а, которую Cloudflare вызывает,
   когда в очереди появилось сообщение. Он читает state, находит завершённые месяцы без файла или с
   устаревшим отпечатком и собирает не больше одного периода за сообщение
   ([02-pipeline.md](02-pipeline.md)). Остался ещё период (в январе — год) — ставит следующее сообщение.
4. **Почему час.** Он переживает и кеш KV (около 60 с), и привычный цикл «прогон → откат → другая модель →
   повтор». Дольше нельзя: на бесплатном тарифе сообщение живёт в очереди 24 часа (сверено с
   документацией Cloudflare; входит ли задержка в эти 24 часа — не проверено).
5. **Порядок выпуска.** Сначала выходит разбор `kind` с подтверждением незнакомого сообщения, и только
   следующим деплоем — постановка в очередь. Сегодня потребитель форму сообщения не проверяет
   (`src/index.ts:49-53`), и старый код принял бы `{ kind: "retro" }` за недельный прогон с неверной датой —
   разбор в [03-privacy-and-failures.md](03-privacy-and-failures.md#откат-деплоя-при-отложенном-сообщении-в-очереди).

Нового cron нет: на бесплатном тарифе их 5 на аккаунт (сверено с документацией), а первого числа последняя
неделя месяца ещё не отчитана.

## Почему это не нарезка недельного прогона

Владелец отклонил нарезку недельного прогона на куски через очередь, и здесь её нет: ретроспектива —
другая, самостоятельная задача, а недельный прогон остаётся одним запуском, как сегодня.

| | Нарезка прогона (отклонена) | Ретроспектива |
|---|---|---|
| Что это | одна задача, разрезанная на куски ради лимита | другая задача: свой вход, свой результат |
| Вход | недоделанное состояние предыдущего куска | готовые отчёты и `history` — всё уже записано |
| Если упала | неделя остаётся наполовину собранной | недельный отчёт уже вышел; нет только файла месяца |
| Пишет state | да, между кусками | никогда; ключей и маркеров в KV не заводит |
| Сколько запусков | десятки в неделю | 13 сборок в год; в остальные недели — до 3 чтений и выход |
| Бюджет | делит лимиты недельного прогона | свой: 50 запросов наружу, 15 минут (сверено с документацией) |

## Пути файлов

Ретроспективы лежат в двух подпапках рядом с недельными отчётами; имя файла однозначно задаёт период.

```
<REPORTS_DIR>/2027-10-08.md          недельный отчёт (как сейчас) + запись недели в конце
<REPORTS_DIR>/2027-10-08_local.md    корректирующий отчёт той же недели, если он был
<REPORTS_DIR>/monthly/2027-10.md     месячная ретроспектива + запись периода в конце
<REPORTS_DIR>/yearly/2027.md         годовая ретроспектива + запись периода в конце
```

Сообщение коммита: `retro: 2027-10`. Запись периода встраивается тем же способом, что запись недели
(маркер `<!-- achievements:record`, `kind: "month" | "year"`); форма — в
[02-pipeline.md](02-pipeline.md#запись-периода-periodrecord). Коммиты робота в работу владельца не
попадают: репозиторий отчётов исключается из сбора в I0-минимуме — до R3 это обязательно.

## Итерации R3 и R4

Две итерации: R3 даёт месяц и всю механику, R4 добавляет второй уровень — год; место в общем порядке — в
[общем README](../README.md).

**До R3 обязательны:** S0 (лог ошибки модели без её ответа — ретроспектива зовёт ту же модель),
I0-минимум (репозиторий отчётов исключён из сбора, `max_concurrency: 1`), R0 и R1 (записи недель и
перевод трёх корректирующих записей в v1).

**R3 (размер M) — месячная ретроспектива.** Что меняется: `src/config.ts` (переменная); `src/index.ts`
(разбор `kind`, маршрут, постановка в очередь); `src/github.ts` (`getFile` и `putFile`, `commitFile`
остаётся обёрткой); общий вызов модели выносится из `src/llm.ts` в `src/llm/call.ts` (файл сегодня 356
строк, функции провайдеров уже принимают схему и инструкции: `src/llm.ts:127`, `224`, `317`); новая папка
`src/retro/` — `types`, `due`, `aggregate`, `strip`, `payload`, `render`, `run`; тексты в `src/i18n/`;
README и `SECURITY.md` проекта. Приёмка:

1. Первый деплой — только разбор `kind`: сообщение без `kind` запускает недельный прогон, как раньше;
   незнакомое подтверждается. Золотой отчёт (эталонный файл в тестах) не изменился.
2. Без переменной: ни одного сообщения в очередь, `/retro` отвечает 404.
3. Повтор с теми же входами: 0 вызовов модели, 0 сообщений в Telegram (тест считает вызовы).
4. Обычный месяц из 5 недель укладывается в 18 запросов наружу даже со вторым вызовом модели и повтором
   Telegram; недельный прогон — по-прежнему +0.
5. Золотой файл месяца на русском и английском с заранее заданным ответом модели; в нём неделя из двух
   файлов показана одной неделей работы.
6. Сбой модели → файл не записан, уведомление ушло, исключение наружу не вышло; `attempts > 1` → 0
   вызовов модели.
7. Неделя режима `full` при текущем `redact` → её текста нет во входе модели, её приватные проекты
   свёрнуты; локальный текст при неподтверждённо приватном репозитории отчётов → только числа.
8. Процессорное время запуска измерено в локальном движке Cloudflare (workerd через `wrangler dev`) и
   записано в README проекта.
9. У владельца: сразу вручную собраны август и сентябрь 2026; оба файла прочитаны, формулировки
   поправлены; принято решение по вопросу №8.

**R4 (размер S–M) — год.** Что меняется: второй читатель (12 месячных файлов и их записи), годовые тексты
и шаблон, шаг «год» в получателе. Приёмка:

1. Сумма месячных записей равна годовой (проверка на случайных сценариях).
2. В январе сначала достраивается декабрь, потом отдельным сообщением год.
3. Месяц без файла, но с записями в `history` сначала достраивается; без записей — строка «нет данных
   за …» и пометка «итог неполный»; молча месяц не пропускается.
4. Первый год подписан «с <месяц>»; хроника строится кодом из заголовков месяцев.
5. Сборка года — не больше 20 запросов наружу; повтор — 0 вызовов модели.

**Жёсткая дата R4 — пятница 1 января 2027.** В этот день недельный прогон впервые получит дату отчёта в
новом году, декабрь 2026 закроется, и через час должен собраться сначала декабрь, потом год. Поэтому при
задержках R4 идёт раньше I2 и I3. Честно о цене опоздания: год собирается из месячных файлов, а не из
`history`, поэтому опоздавший R4 лечится одной командой `POST /retro?period=2026` — пропадает только
момент, файл не теряется. По-настоящему невосполнимо другое: месяц можно собрать, только пока его недели
лежат в окне 53 недель, поэтому R3 нельзя откладывать на год.

## Что отклонено

Отклонено всё, что добавляло хранилище, запрос в недельный прогон или платный повтор.

| Вариант | Почему нет |
|---|---|
| Отдельный cron первого числа | Слот из пяти; правка трёх конфигов; последняя неделя месяца ещё не отчитана |
| Сборка внутри недельного прогона | Делит с ним лимит запросов и процессорное время; общий сбой |
| Признак «файл существует — значит, сделано» | Не замечает пересобранную неделю; владельцу пришлось бы помнить про `force` |
| Отпечаток по git-идентификаторам файлов, список папки через GraphQL | Второй путь чтения; правка опечатки в отчёте руками запускала бы платную пересборку |
| Маркер «сделано» в state или KV | Откатывался бы вместе с `DELETE /state/latest`; ломает цепочку «один снимок — один прогон» |
| Повторы ретроспектив через `message.retry`, `max_retries` в конфигах | До трёх платных вызовов на один сбой; правка трёх конфигов wrangler |
| Неделя относится к месяцу по середине периода | Свежая неделя попадала бы в только что закрытый месяц — откат и повтор портили бы готовый файл |
| Ретроспектива «только из чисел» при сбое модели | Файл появился бы, и отпечаток счёл бы месяц готовым |
| Год из 52 недельных отчётов; сравнение «год к году» | Больше 50 запросов и сотни тысяч знаков; сравнение — не раньше второго года |
| `RETROSPECTIVES` включена по умолчанию | У форков без новых переменных появились бы платные вызовы и сообщения |

## Журнал решений

Все решения приняты в один день — по итогам сравнения трёх вариантов дизайна и их независимой проверки.

| Дата | Решение | Почему |
|---|---|---|
| 2026-09-19 | Одна переменная `RETROSPECTIVES`, по умолчанию `false` | Платные вызовы и сообщения — только по явному включению (P6) |
| 2026-09-19 | Запуск сообщением в существующую очередь через час после недельного прогона | Свой запуск со своим бюджетом: сбой физически не может уронить недельный отчёт (P5); нового cron нет |
| 2026-09-19 | Получатель сам вычисляет период из state в момент запуска | Откат недели, поставившей сообщение, безвреден |
| 2026-09-19 | Неделя относится к месяцу по локальной дате своего `until` | Объясняется одной фразой, для прогонов по расписанию совпадает с именами файлов; закрытый месяц не содержит самую свежую неделю |
| 2026-09-19 | Повтор ничего не тратит — по отпечатку входов из `history`; в отпечатке нет времени, модели, версии словаря | Еженедельная проверка не превращается в платный вызов; пересобранная неделя обновляет месяц сама |
| 2026-09-19 | Ретроспектива не пишет state и не заводит ключей KV | `DELETE /state/latest` по-прежнему снимает именно неделю |
| 2026-09-19 | Две недели-файла — одна неделя работы; часы складываются | Корректирующие отчёты посчитаны на общей шкале времени с основными (`hoursScale`) |
| 2026-09-19 | Текст корректирующего отчёта отдаётся модели наравне с основным | Решение владельца: для своего сервера — режим `text` у всех репозиториев; защищает проверка приватности репозитория отчётов |
| 2026-09-19 | Текущий режим приватности строже режима недели → от недели только числа | Иначе ретроспектива перепечатала бы старый приватный текст в новый файл, в модель и в Telegram |
| 2026-09-19 | Чтение — REST по именам из `history`; `commitFile` делится на `getFile` и `putFile` | Список папки не нужен; `GITHUB_TOKEN` в запуске не участвует |
| 2026-09-19 | Год — сумма месячных записей; недостающий месяц достраивается или называется | Молчаливый пропуск занижал бы итог года |
| 2026-09-19 | При `message.attempts > 1` модель повторно не вызывается | Повторная доставка после жёсткого падения иначе дала бы до четырёх платных вызовов |
| 2026-09-19 | Сначала разбор `kind`, потом постановка в очередь | Старый код принял бы сообщение за недельный прогон с неверной датой |

### Принятые допущения

Там, где решения от 2026-09-19 молчали, выбран самый простой путь; всё ниже дёшево изменить, подробности — в
[02-pipeline.md](02-pipeline.md) и [03-privacy-and-failures.md](03-privacy-and-failures.md).

1. Автоматически проверяются три самых свежих закрытых месяца, а не всё окно `history`; год — только в
   январе. Если номеров недель из готового файла в `history` нет вовсе, автоматической пересборки нет.
2. После успешной сборки — следующее сообщение через 60 секунд; список `built` не даёт собрать период
   дважды. Ручной запуск собирает один период без цепочки и отвечает 409 на незакрытый период.
3. Список корректирующих отчётов в отпечатке автоматически не сравнивается; поздний корректирующий отчёт —
   повод для `force=1`.
4. Месяц берётся по поясу `tz` записи недели; закрытие месяца — по текущему `TIMEZONE`.
5. Корректирующая запись без пометки `hoursScale` в сумму часов не входит; файл без читаемой записи не
   учитывается. Активные дни — объединение дней из записей, иначе сумма со знаком «≈».
6. Ссылки в текстах для модели заменяются их текстом; потолок 12 000 знаков один для недельных и месячных
   файлов; промпт получает тот же `DEV_PROFILE`, что недельный.
7. При текущем `skip` итоги недель, записанных мягче, входят как записаны (со сноской).
