## Главное за минуту

Ретроспектива не может раскрыть больше, чем уже лежит в репозитории отчётов, но может это **повторить** — в
новом файле, у провайдера модели и в Telegram; три правила не дают повторить лишнее, а любой сбой
оставляет недельные отчёты нетронутыми.

1. Текущий режим приватности строже режима недели → от этой недели берутся только числа.
2. Во входе есть текст локальных репозиториев → ретроспектива сама проверяет, что репозиторий отчётов
   приватный; не подтверждено → только числа.
3. Перед моделью весь вход проходит поиск секретов; нашлось то, что не удалось вычистить, → отказ от вызова.

При любом сомнении действует общий принцип проекта «при сомнении — скрыть». Общая картина приватности —
в [../local-sources/02-privacy.md](../local-sources/02-privacy.md).

## Текущий режим строже режима недели

Ретроспектива подчиняется режиму `PRIVATE_REPOS`, который действует **сейчас**, а не тому, при котором
писалась неделя: режим недели лежит в её записи (`privacy`), порядок строгости — `full` → `redact` → `skip`.

| Режим недели | Режим сейчас | Что берётся от недели |
|---|---|---|
| тот же или строже текущего | любой | всё: числа и текст отчёта |
| `full` | `redact` | только числа; текст модели не отдаётся; проекты с флагом `private` уходят в строку «приватные проекты» |
| `full` или `redact` | `skip` | только числа; приватные строки не печатаются; итоги недели входят как записаны — приватную часть из них уже не вычесть, об этом сноска *(принятое допущение)* |
| в записи нет `privacy` | любой, кроме `full` | как самая мягкая неделя: только числа |

- **Зачем.** Репозиторий отчётов могли сделать публичным или ужесточить режим уже после того, как неделя
  записана. Старый отчёт с именами остаётся на совести владельца репозитория (чистка истории git — его
  решение), но новый файл, вход модели и сообщение в Telegram повторять эти имена не должны.
- **То же для корректирующего файла:** у его записи свой `privacy`, правило применяется к нему отдельно.
- **«Только числа» на деле:** в данных для модели у недели `report: null`; в «Из чего собрано» — пометка
  «только числа»; в таблицах и в записи периода её приватные проекты свёрнуты в одну строку без имён.
- Обратное не действует: если сейчас режим мягче, имена, скрытые при записи недели, не возвращаются — в
  записи недели их просто нет.

## Локальный текст и проверка приватности репозитория отчётов

Текст локальных репозиториев попал в отчёты только потому, что в ту пятницу Worker подтвердил: репозиторий
отчётов приватный; перед тем как нести этот текст дальше, ретроспектива проверяет это заново и сама.

- **Когда нужна проверка:** среди записей месяца есть строка проекта с `local: true`, с именем и без
  `counters` — то есть локальный проект с текстом. Это корректирующие отчёты и общие отчёты после I1.
- **Как:** один запрос сведений о репозитории отчётов токеном отчётов (после I1 — готовая функция
  `checkReportsRepo`). Закэшированный ответ проверочного запроса (`ingest:v1:policy`) не используется:
  проверка живая, как в недельном прогоне. Прав токена отчётов на этот запрос хватает — проверено живым
  запросом ([04-findings](../local-sources/04-findings.md#git-проверено-на-тестовых-репозиториях-git-247)).
- **Подтверждено** только при явном ответе «приватный». Ошибка сети, 403, 404, непонятный ответ — не
  подтверждено.
- **Не подтверждено →** у корректирующих файлов `local: null`; у общего отчёта с локальным текстом весь
  `report: null` (локальный текст нельзя отделить от остального, не разбирая вёрстку); именованные
  локальные проекты сворачиваются. В логе — `retro_text_withheld` с номерами недель и причиной, без имён.
- Репозитории в режиме «только цифры» текста не несут и проверки не требуют; «не собирать» не оставляет
  следа и здесь.

Решению владельца — режим `text` для всех репозиториев своего сервера — проверка не мешает: пока репозиторий
отчётов приватный, она проходит, и текст корректирующего отчёта идёт модели наравне с основным.

## Поиск секретов и то, что уходит модели

Вход модели собирается заново из файлов, которые могли править руками, поэтому проходит ту же защиту, что
недельные данные, — отдельным списком ключей, чтобы недельную защиту не трогать.

1. `stripForRetro`: без `<details>`, без HTML-комментариев, ссылки заменены своим текстом,
   `private-project-N` (`src/privacy.ts:36`) → «приватный проект» — номер в каждом отчёте свой, и связывать
   по нему недели нельзя.
2. Словарь замен, если он задан (итерация A1); без словаря шаг пуст.
3. `scrubSecrets` (`src/secrets.ts:70-75`) заменяет похожее на секрет на `[secret]`; затем обрезка до
   12 000 знаков.
4. `buildRetroPayload`: свой список разрешённых ключей в `src/retro/payload.ts`. Недельный список
   (`src/sanitize.ts:92-116`) не меняется — он бросает исключение на любом новом ключе, и правка ради
   ретроспективы рисковала бы недельным отчётом.
5. `assertNoSecrets` по всему входу (`src/secrets.ts:88-102`). Что-то осталось → исключение → модель не
   вызывается. Это обычный сбой: файл не пишется, уходит уведомление; в ошибке — имя правила и путь, но
   не сама находка.
6. После ответа: пункты о проектах, которых не было во входе, отбрасываются; подметание словарём, если
   он задан; встраивание записи — после подметания, как в недельном отчёте.

Честные оговорки. Длинные адреса ссылок похожи на случайные строки, и детектор секретов мог бы затирать
их — поэтому ссылки убираются до него (на золотых файлах ещё не проверено). Отчёт, отредактированный
руками, — это чужой текст во входе модели; у модели нет инструментов, худшее следствие — формулировки
ретроспективы.

## Данные в покое и логи

Нового хранилища нет: появляются только файлы в репозитории отчётов, а тексты отчётов второй раз уходят
тому же провайдеру модели.

| Где | Что нового |
|---|---|
| Репозиторий отчётов | `monthly/`, `yearly/`: текст и запись периода — имена проектов по текущему режиму, числа, заголовок. Невидимый комментарий виден в сыром файле |
| KV | ничего: ни ключей, ни полей state |
| Провайдер модели | очищенные тексты 4–5 недельных (или до 12 месячных) отчётов; тот же провайдер и то же правило «без хранения данных», что у недельного вызова |
| Логи Workers | события `retro_*`; на путях ошибок — только тип ошибки. Обязательное условие — исправление S0: сегодня лог ошибки модели содержит её причину целиком (`src/llm.ts:214`) |
| Сохранённые трассы Cloudflare | адреса запросов: имя репозитория отчётов, имена файлов (даты) и адрес Telegram — как у недельного прогона; вопрос №3, [../local-sources/08-threat-model.md](../local-sources/08-threat-model.md) |

## Когда модель не ответила

Файл не пишется, в Telegram уходит короткое уведомление без текста ошибки, следующая попытка — в
следующую пятницу; ретроспектива «только из чисел» не выпускается.

- Порядок попыток тот же, что у недельного вызова: строгий ответ по схеме → у OpenRouter второй,
  текстовый вызов (`src/llm.ts:310-333`). Не вышло — исключение, которое получатель ловит сам.
- Уведомление: «Ретроспектива за октябрь 2027 не собрана. Повторю в следующую пятницу; вручную —
  `POST /retro?period=2027-10`». Это новая строка в `src/i18n/`; нынешнее уведомление говорит о недельном
  отчёте (`src/telegram.ts:21-27`) и сюда не годится.
- Почему без файла «только из чисел»: файл с отпечатком считался бы готовым, и повтора бы не было.
- Худший случай: модель стабильно не попадает в схему — один платный вызов и одно уведомление в неделю,
  пока владелец не вмешается (сменит модель или выключит переменную). Принято осознанно ради простого
  правила повтора.
- Если падение случилось после ответа модели, но до записи файла, вызов оплачен впустую; следующая пятница
  повторит его. Недельный отчёт к этому моменту уже час как вышел.

## Повторная доставка очереди и `message.attempts`

Обычную ошибку получатель ловит сам и сообщение подтверждает; повторно его доставляет только платформа
после жёсткого падения — и тогда модель второй раз не вызывается.

Сверено с документацией Cloudflare: по умолчанию сообщение доставляется повторно до трёх раз
(`max_retries` в конфигах не задан: `wrangler.jsonc:46-49`); при падении обработчика повторяется вся
пачка (она из одного сообщения: `max_batch_size: 1`); `message.attempts` начинается с 1. Жёсткое падение —
это превышение процессорного времени или 15 минут: `try/catch` его не ловит.

```ts
async function handleRetro(env: Env, message: Message<RetroMessage>): Promise<void> {
  try {
    if (!loadConfig(env).retrospectives) return log("retro_disabled");
    if (message.attempts > 1) {                        // прошлую попытку оборвала платформа
      log("retro_redelivered"); await notifyRetroFailed(env);
      return;                                          // модель повторно НЕ вызывается
    }
    await runRetro(realDeps(env), message.body);
  } catch (err) {
    log("retro_failed", errorType(err));               // только тип ошибки, без её текста
    await notifyRetroFailed(env, periodOf(err)).catch(() => {});   // период называется, если он уже известен
  } finally {
    message.ack();                                     // для kind: "retro" — подтверждение всегда
  }
}
```

Без проверки `attempts` одно жёсткое падение после вызова модели дало бы до четырёх платных вызовов без
единого уведомления. Настройки очереди в конфигах wrangler не меняются; для `kind: "retro"` `message.retry` не
используется. Сообщения недельного прогона обрабатываются так же, как до R3 (с I0-минимума — защита в `runWeekly`
и один повтор через 90 с, см. [06-change-map](../local-sources/06-change-map.md#изменения-в-существующих-файлах-src)).

## Откат деплоя при отложенном сообщении в очереди

Если откатить Worker на версию, которая ещё не знает `kind`, а в очереди лежит отложенное
`{ kind: "retro" }`, старый код примет его за недельный прогон; вред — одно ложное сообщение об ошибке.

Что произойдёт (проверено чтением кода): потребитель не смотрит на форму сообщения и строит дату из
отсутствующего `until` (`src/index.ts:49-52`) → неверная дата доходит до расчёта периода
(`src/run.ts:34-38`) → `since.toISOString()` бросает исключение (`src/github.ts:193`) **до** любой записи →
`runInBackground` пишет `run_failed` и шлёт «еженедельный отчёт не сформирован» (`src/index.ts:33-39`).
Файлы и state не тронуты.

| Защита | Что даёт |
|---|---|
| Двухшаговый выпуск: сначала разбор `kind` и подтверждение незнакомого, следующим деплоем — постановка в очередь | Откат на одну версию назад попадает в код, который уже умеет тихо подтвердить такое сообщение |
| Короткие задержки: 1 час и 60 секунд | Опасное окно — час после недельного прогона, а не полсуток |
| Правило эксплуатации (записано рядом с другими откатами в [05-operations](../local-sources/05-operations.md#откат-деплоя-и-потеря-kv)) | Перед откатом на версию старше R3 — выключить `RETROSPECTIVES` и выждать час; если не вышло — одно ложное уведомление можно не замечать |
| Версия с разбором `kind`, но выключенной переменной | Подтверждает сообщение без работы |

Обратное безопасно: новый код, получивший старое сообщение `{ until }`, запускает недельный прогон. Деплой
кода **старше I0-минимума** опасен другим — он стирает `history` (код новее переносит её как есть, только без
недель старого кода — [подробнее](../week-record/02-backfill-and-recovery.md#деплой-старого-кода)); на этот
случай есть правило «входы сократились» в таблице сбоев ниже.

## Недостающие месяцы в году

Год — сумма месячных записей, поэтому годовой шаг сначала проверяет все месяцы года и ни один не
пропускает молча: месяц либо достраивается, либо назван.

| Что с месяцем | Что делает годовой шаг |
|---|---|
| Файл есть, запись читается | Входит в год |
| Файла нет, в `history` есть записи его недель | Сначала достраивается месяц — это единственная сборка сообщения; год идёт следующим сообщением цепочки |
| Файла нет (или запись не читается), записей в `history` нет | Строка «нет данных за …», месяц — в `missing`, в шапке «итог неполный» (`partial`) |
| Месяцы до первого месяца с данными | Не перечисляются: первый год подписан «с <месяц>» |
| Декабрь не собрался из-за сбоя | Года нет: каждую пятницу января получатель снова пробует декабрь и до года не доходит; после января — ручной маршрут |

```markdown
# <REPORT_TITLE> — 2028 год

_Недели #27–#78 · 31 дек. 2027 г. — 29 дек. 2028 г. · 11 месяцев из 12 · итог неполный_
…
- **Апрель** — …
- **Май** — нет данных: ретроспектива месяца не собрана, а его недели уже вышли из окна истории.
- **Июнь** — …
```

Опоздавший R4 лечится вручную (`POST /retro?period=2026`): году нужны месячные файлы, а не `history`.
Месяцу же нужна `history` — поэтому месяц, не собранный за год, становится строкой «нет данных».

## Остальные сбои

Каждый сбой оставляет либо готовый файл, либо ничего — наполовину записанной ретроспективы не бывает.

| Что случилось | Что происходит |
|---|---|
| Постановка в очередь не удалась | Лог `retro_enqueue_failed`; неделя уже выпущена; следующая пятница поставит снова |
| Сообщение потеряно (очередь недоступна дольше 24 часов) | То же; есть ручной маршрут |
| Недельный файл не найден (404) | Неделя идёт только числами; пометка в «Из чего собрано» |
| Ошибка GitHub при чтении (403, 5xx) | Сбой сборки: файла нет, уведомление, повтор через неделю |
| `putFile` получил 409 | Один повтор со свежим `sha`; снова 409 → сбой сборки |
| Telegram не принял сообщение, файл уже записан | Файл остаётся, отпечаток говорит «готово»; лог `retro_notify_failed`; повторно не шлём |
| Номеров недель из `inputs` готового файла в `history` нет вовсе: они меньше наименьшего `n` в `history` или `history` пуста (потеря KV, деплой кода старше I0-минимума, недели вышли из окна) | Автоматической пересборки нет: лог `retro_inputs_shrunk`, уведомление; лечится `records-rebuild` или `force=1` *(принятое допущение)*. Номер в `history` есть, но ушёл в другой месяц или изменился → обычная пересборка с пометкой «обновлено» |
| У недели нет записи (`record_failed` в ту пятницу) | В `history` её нет — в месяц она не попадает; в шапке виден пропуск номера |
| Ретроспектива совпала по времени с пятничным прогоном | Cron идёт мимо очереди, `max_concurrency: 1` их не разводит. State ретроспектива только читает; общий ресурс — репозиторий отчётов: одновременные записи могут дать 409 одной из сторон, а у недельного `commitFile` повтора нет. Автоматический запуск отстоит от прогона на час; вручную `/retro` около времени cron в пятницу не запускать |
| Период из `built` снова оказался «не готов» | Лог `retro_loop_guard`, цепочка останавливается, уведомление |

## Тесты и свойства

Всё, кроме короткого кода, принимающего сообщения очереди, — чистые функции; получатель проверяется целиком на подставных
зависимостях, без сети.

- **Чистые функции без `Env`:** `duePeriods`, `assignMonth`, `aggregatePeriod`, `aggregateYear`,
  `stripForRetro`, `buildRetroPayload`, `filterAnswer`, `renderPeriod`, встраивание и чтение записи периода.
- **`runRetro(deps, message)`**, где `deps = { loadState, getFile, putFile, callModel, notify,
  checkReportsPrivate, enqueue, now }` — подделки считают вызовы.
- **Проверка на случайных сценариях** (сотни выдуманных историй, зерно генератора фиксировано, без новых
  зависимостей; тесты идут под vitest, как остальные):
  1. сумма недель равна месяцу — по каждому складываемому полю, с корректирующими записями;
  2. сумма месяцев равна году;
  3. каждая неделя — ровно в одном месяце; закрытый месяц не содержит самую свежую неделю;
  4. перенос опоздавшей работы сохраняет суммы (общее свойство с трендами: месяц считает по неделе доставки);
  5. повтор с теми же входами — 0 вызовов модели и 0 сообщений; откат и повтор недели, закрывшей месяц,
     не меняют его отпечаток; двойной откат такой недели → месяц пересобран, сумма месяцев = сумма недель;
  6. `records-rebuild(отчёты)` равен истории, ведённой по ходу, — на случайных последовательностях с

  7. цепочка сообщений конечна: ни один период не собирается в ней дважды.
- **Счётчик запросов наружу:** неделя +0; обычный месяц ≤ 18; год ≤ 20.
- **Тесты-канарейки** (в данные заранее подложена приметная строка): имя приватного проекта при `redact` не
  встречается во входе модели, в файле и в записи периода; неделя `full` при текущем `redact` не даёт ни
  имён, ни текста; локальный текст при неподтверждённой приватности → `null`; `private-project-7` во входе

  `attempts > 1` → 0 вызовов модели; 409 → ровно один повтор; выключенная переменная → подтверждение без работы.
