# 01. Схема записи недели, версия 1

> **Для кого:** тот, кто пишет код R0 и R1, и авторы трендов и ретроспектив — они читают эти поля.
> **Что здесь решает владелец:** порог массового коммита (вопрос №9) и согласие с тем, что часы попадают в
> запись даже при выключенной оценке зарплаты (вопрос №5) — оба в [общем README](../README.md).
> **Что просто к сведению:** остальное — описание принятой схемы. «Принятое допущение» помечает места, где
> решения от 2026-09-19 молчали и выбран самый простой вариант.

Зачем запись и где лежит — в [README](README.md). Ссылки `src/файл:строка` проверены чтением кода 2026-09-19.

## Схема целиком

Одна плоская запись на неделю; всё необязательное помечено `?` и может отсутствовать.

```ts
export interface WeekRecord {                 // src/record/types.ts
  v: 1;
  kind: "week" | "corrective";          // corrective — файл <день>_local.md
  n: number;                            // номер отчёта; у corrective — номер основной недели
  since: string; until: string;         // ISO, UTC
  days: number;                         // длина периода в сутках
  generatedAt: string; tz: string;
  privacy: "full" | "redact" | "skip";  // режим на момент записи
  sources: ("github" | "local" | "sessions")[];
  llm: string;                          // "provider/model"
  hoursAlgo: number;                    // версия метода расчёта часов
  src?: "backfill";                     // восстановлено из старого отчёта
  commits: number; additions: number; deletions: number;
  prs: number; issues: number;          // как в отчёте; по месяцам НЕ складываются
  prsOpened: number; prsMerged: number; issuesOpened: number; issuesClosed: number; // складываются
  ci: [ok: number, fail: number]; deployments: number;
  activeRepos: number; activeDays: number;
  minutes: number; capped: boolean;     // сфокусированные минуты после всех ограничений
  est: [fromModel: number, fallback: number];
  bulk?: { threshold: number; commits: number; additions: number; deletions: number };
  late?: Record<string, { commits: number; minutes: number }>; // ключ — номер недели; "0" — старше истории
  dayMap?: Record<string, [commits: number, minutes: number]>;  // локальная дата → [коммиты, минуты]
  projects: { name: string | null; repos?: number; commits: number; additions: number; deletions: number;
              minutes: number | null; private?: true; local?: true; counters?: true }[];
  achievements: string[]; streak: number;
  cost?: { currency: string; employee: number; freelance: number };
  local?: { commits: number; late: number; deferred: number; expired: number };            // заполняет I1
  ai?: { minutes: number; sessions: number; byProject?: { name: string | null; minutes: number }[] }; // I3
  hoursScale?: "union-with-main-report"; // только у corrective — см. «Корректирующие записи»
}
```

Пример на выдуманных данных, режим `redact` (в файле — одной строкой; в `dayMap` только нескрытый проект):

## Поля: смысл, источник, почему не восстановить позже

Каждое поле либо уже считается в прогоне и сегодня выбрасывается, либо стоит одну строку кода; колонка
«Позже» объясняет, почему его нельзя добыть задним числом.

| Поле | Смысл | Откуда значение | Позже |
|---|---|---|---|
| `v`, `kind` | версия схемы; обычная неделя или корректирующий файл | константа; кто вызвал `buildWeekRecord` | — |
| `n` | номер отчёта | `state.reportCount + 1` (`src/report.ts:37`) | есть в заголовке, но заголовок — текст на языке отчёта |
| `since`, `until` | границы периода | `week.since`, `week.until` (`src/run.ts:34-38`, `src/github.ts:263-264`) | в отчёте только даты без времени (`src/report.ts:42`); время нужно для опоздавших и для правила «какая запись главная» |
| `days` | `(until − since)` в сутках, до 0,1 | вычисляется | производное; хранится, чтобы читатель не считал |
| `generatedAt` | когда собрана запись | момент прогона; передаётся параметром, чтобы функция оставалась чистой | только из истории git |
| `tz` | часовой пояс, в котором посчитаны дни | `config.timezone` (`src/config.ts:90`) | `TIMEZONE` может смениться при переезде |
| `privacy` | режим `PRIVATE_REPOS` в момент записи | `config.privacy` (`src/config.ts:95`) | иначе старую неделю `full` не отличить от `redact` — на этом стоит правило «сейчас строже → только числа» |
| `sources` | из чего собрана неделя | R0: всегда `["github"]`; I1 добавляет `local`, I3 — `sessions` | нужно для разрыва ряда |
| `llm` | кто оценивал минуты | `config.llm` (`src/config.ts:97-99`), как подпись в `src/report.ts:175` | подпись есть в тексте, но текстом |
| `hoursAlgo` | версия метода расчёта часов | новая константа `HOURS_ALGO_VERSION = 1` в `src/hours.ts` | метод уже менялся: `src/hours.ts` появился 2026-09-12 |
| `src` | `"backfill"` — запись восстановлена из старого отчёта, часть полей приблизительна или пуста | скрипт R1 | — |
| `commits`, `additions`, `deletions` | как в таблице итогов отчёта | `week.total*` (`src/github.ts:268-270`; при `skip` пересчитаны без приватного, `src/privacy.ts:25-27`) | в отчёте — текст с пробелами внутри чисел |
| `prs`, `issues` | как в отчёте; **по месяцам не складывать** | `week.prs.length`, `week.issues.length` (`src/report.ts:52-53`) | — |
| `prsOpened` … `issuesClosed` | события внутри `[since, until)`; складываются | новые даты из ответа поиска — раздел ниже | дат в отчёте нет, а PR со временем меняется |
| `ci`, `deployments` | прогоны CI [успешные, упавшие]; деплои | суммы по репозиториям (`src/report.ts:60-62`); CI читается только у первых `MAX_CI_REPOS` репозиториев (`src/github.ts:215`) | в отчёте — текстом |
| `activeRepos` | репозиториев с коммитами | `week.repos.length` (`src/report.ts:65`) | — |
| `activeDays` | сколько разных локальных дней с коммитом | время работы коммита — `authoredDate`, иначе `date`, как в `src/hours.ts:43-47`, — в поясе `tz` | даты коммитов после отчёта остаются только в списках под `<details>`, а у скрытых репозиториев нет и их (`src/report.ts:90-94`) |
| `minutes` | сфокусированные минуты недели после всех ограничений | `min(сумма perCommit, 60 ч)` из `resolveHours` (`src/hours.ts:98-122`) | в отчёте часы видны, только когда включена оценка зарплаты (`src/report.ts:128`) |
| `capped` | сработал недельный потолок 60 ч | `hours.capped` (`src/hours.ts:95`) | сегодня только в логе, лог живёт 3 дня |
| `est` | сколько коммитов оценила модель, сколько — запасная формула | `hours.fromModel`, `hours.fallback` (`src/hours.ts:92-93`) | сегодня только в логе `hours_estimate` (`src/run.ts:52-61`) |
| `bulk` | какая часть строк пришлась на массовые коммиты | строки каждого коммита (`src/types.ts:7-8`) — раздел «Строки» | разбивки строк по коммитам в скрытых репозиториях в отчёте нет |
| `late` | работа, написанная до `since` | даты коммитов + `history` — раздел «Опоздавшие» | дат нет, границы старых недель уходят из окна 53 |
| `dayMap` | локальная дата → [коммиты, минуты] | то же время работы + минуты по коммитам (`perCommit`, `src/hours.ts:90`) | нужен, чтобы «активные дни» месяца считались объединением дней, а не суммой недель: пятница на границе иначе считается дважды |
| `projects[]` | строка на проект: имя, коммиты, строки, минуты | `week.repos`; минуты — сумма `perCommit` по `timeline[].repo` (`src/hours.ts:31`); при срабатывании потолка 60 ч уменьшаются пропорционально | **минут по проектам в отчёте нет вообще** |
| `achievements`, `streak` | id ачивок этой недели; серия после неё | `src/run.ts:43-44, 71` | названия ачивок в отчёте — переводимый текст |
| `cost` | стоимость недели, как в отчёте | `computeWeekCost` (`src/cost.ts`), только при включённой оценке зарплаты | ставки меняются, позже не пересчитать |
| `local` | счётчики локальных источников | заполняет I1 | снимки с машин живут 9 дней |
| `ai` | «время в паре с ИИ»; **никогда не складывается с `minutes`** | заполняет I3 | записи сессий живут около 30 дней |

В `projects[]`: `private: true` — приватный репозиторий, показанный по имени (режим `full`); `local: true` —
проект из локального источника; `counters: true` — репозиторий в режиме «только цифры»; у строки
`name: null` поле `repos` говорит, сколько проектов в неё свёрнуто. У записей из бэкфилла `minutes: null`.

## Приватность: что попадает в запись

Запись строится только из недели после `applyPrivacy` (и после словаря замен, если он задан), поэтому в ней
нет ничего, чего нет в объекте, из которого строится видимый отчёт (принцип P4).

| | `full` | `redact` (по умолчанию) | `skip` |
|---|---|---|---|
| Имена проектов | настоящие; у приватных флаг `private` | публичные — настоящие; **все** приватные — одна строка `name: null, repos: N` | приватных нет вовсе |
| Итоги, минуты, счётчики PR и issues | всё | всё, включая приватное, — как и в видимой таблице итогов | без приватного |
| `dayMap` | все дни | только дни **нескрытых** репозиториев | без приватного |
| `late`, `activeDays` | одним числом, без имён | одним числом, без имён, включая скрытое | без приватного |

- **Нестабильные имена.** Всё, что подходит под `private-project-N` (`src/privacy.ts:36`) и `project-N`, идёт
  в одну строку без имён, номеров и хешей: номер выдаётся заново в каждом отчёте, склеивать недели по нему
  нельзя. Псевдонимов (HMAC) не делаем. *Принятое допущение:* «скрытый» для `dayMap` — попавший в `name: null`.
- **Локальные репозитории (I1).** «Только цифры» при `full` — строка `local/<id>` с флагом `counters`; при
  `redact` — в общей строке `name: null`. «Не собирать» не оставляет следа нигде, включая `ai`.
- **Даты PR и issues — не текст.** Сегодня `redactPrivate` копирует объекты целиком (`src/privacy.ts:58-63`),
  и новые поля переживают скрытие сами; когда I0 введёт явные списки полей, даты вносятся в них. В данные
  для модели они не попадают: там явная проекция (`src/sanitize.ts:153-158`).
- **Публичный репозиторий отчётов (у чужого форка).** Комментарий не показывается на странице, но виден в
  сыром файле. Сверх видимого отчёта запись раскрывает: минуты (общие, по проектам и свёрнутой приватной
  строки), `dayMap`, `est`, событийные счётчики. Это видимое изменение поведения: называется в README в
  списке «Изменения поведения» и в `SECURITY.md` (вопрос №5).
- **Если режим со временем ужесточился,** читатели подчиняются **текущему** режиму: строки с флагом `private`
  сворачиваются, текст такой недели модели не отдаётся — [подробнее](../retrospectives/03-privacy-and-failures.md).

## Версии

Старые файлы не переписываются никогда; вся терпимость — на стороне читателя.

1. Сейчас `v: 1`. Добавление **необязательного** поля версию не меняет.
2. Читатель терпим к незнакомым полям и никогда не бросает исключение.
3. Запись с версией выше поддерживаемой для чтения считается отсутствующей, но `appendHistory` переносит
   её в новый снимок как есть — откат кода на шаг назад историю не стирает.
4. Смена смысла или типа поля → `v: 2` и чистая функция пересчёта при чтении; она пишется, когда
   понадобится, не раньше. В `history` версии могут лежать вперемешку.
5. Золотой JSON каждой версии лежит в тестах; тест читает каждый и поднимает до текущей версии.
6. Маркер `<!-- achievements:record` неизменен; если блоков несколько, читается последний.

## PR и issues: два вида счётчиков

Старые `prs` и `issues` складывать по месяцам нельзя, поэтому рядом с первой же записи лежат событийные.

Сегодня PR и issues отбираются по `updated:>=since` (`src/github.ts:201-202`): PR, в котором что-то менялось
три недели подряд, попадает в три отчёта, и сумма за месяц была бы завышена. R0 добавляет необязательные
`PrInfo.createdAt/mergedAt/closedAt` и `IssueInfo.createdAt/closedAt`; значения берутся из того же ответа
поиска — новых запросов нет. По ним считаются события внутри `[since, until)`: `prsOpened`, `prsMerged`,
`issuesOpened`, `issuesClosed`. Месяц и год складывают только их. PR, закрытый без слияния, в `prsMerged`
не входит. Существующее ограничение остаётся: поиск отдаёт не больше 50 элементов (`src/github.ts:178`).

## Строки: два правила

Строки загруженных извне документов — не объём работы, а трендов и рекордов по строкам нет вообще. Повод —
находка: git считает текстом PDF и письма, такие файлы дают сотни тысяч «строк».

**Правило 1 — локальные коммиты (I1).** Collector по списку файлов коммита (имена файлов остаются в памяти
машины) отделяет загруженные документы по расширению: PDF, письма, офисные файлы, lock-файлы. В отчёте и в
записи показывается «сырые − загруженные». **В отправляемом снимке при этом остаются сырые `additions` и `deletions`**,
а вычтенное едет рядом необязательным `imported: [add, del]`. Причина — ключ отсева дублей `K` («секунда
автора + добавлено + удалено», [../local-sources/07-selection.md](../local-sources/07-selection.md)): он
обязан получаться одинаковым на любой машине и в любой версии collector'а. Если бы в `K` входили уже
очищенные числа, изменение списка расширений дало бы тому же коммиту другой `K` — и коммит был бы учтён
дважды. Поэтому `K` считается **только по сырым числам**.

**Правило 2 — коммиты GitHub.** Списка файлов у Worker'а нет, поэтому порог: коммит, у которого
`additions + deletions ≥ BULK_COMMIT_LINES` (10 000), считается массовым, его строки складываются в `bulk`.
Порог лежит внутри записи, потому что может измениться (вопрос №9); на старые записи новое значение не действует.

*Принятое допущение о том, как читать числа:* `additions` и `deletions` верхнего уровня — то, что показано в
таблице итогов отчёта; `bulk` говорит, какая их часть массовая; «строки работы» — разность, её считает
читатель. Правила не пересекаются: локальные коммиты — только правило 1, GitHub — только правило 2. Часы
массовые коммиты не раздувают: у каждого коммита есть потолок окна (`src/hours.ts:21`).

## Опоздавшие коммиты

Запись отвечает на вопрос «к какой неделе отнести работу на графике» и больше ни на какой.

- `late` считается в момент записи: коммиты со временем работы раньше `since`; ключ — номер `n` той
  записи `history`, в чей период попало это время; `"0"` — старше известной истории (или `history` пуста).
- Работает и при скрытых репозиториях: даты скрытие переживают (`src/privacy.ts:53-54`), имён в `late` нет.
- До I1 в `late` попадают только перебазированные коммиты (дата автора старая, дата коммиттера свежая).
  «Поздно запушенных» GitHub-коммитов здесь не бывает: GitHub отбирает по дате коммиттера
  (`history(since:)`, `src/github.ts:116`). После I1 основной источник — локальные коммиты со спавшей машины.
- На графике трендов значение недели = своё − свои опоздавшие + опоздавшие, приехавшие к ней позже
  ([../trends/02-computation.md](../trends/02-computation.md)). Суммы месяца — по неделе доставки.
- Два независимых механизма: журнал учтённого (ledger) отвечает за «не учесть дважды», запись недели —
  за «к какой неделе отнести на графике». Серия и ачивки задним числом не чинятся.

## Неровные недели и разрыв ряда

Сравниваются только похожие недели: близкие по длине (`days`) и посчитанные одинаково (`sources`, `hoursAlgo`).

**Длина.** Ручные прогоны дают недели по 6 и 8 дней, догоняющий (после пропущенных пятниц) — до 28 (`src/run.ts:25-38`).
**Сравнима** запись с `5 ≤ days ≤ 9,5`: только такие входят в «обычное» значение и в рекорды, с пересчётом на
7 дней (`x × 7 / days`) — лишь для сравнения и высоты столбика; в тексте — реальные числа с пометкой
«(8 дней)». Всё, что не 5–9,5 дня (догоняющий прогон, короткий отчёт), — вне сравнений. В суммы месяца всё входит как есть.

**Разрыв ряда.** «Обычно», рекорды и строка в Telegram считаются только среди записей с тем же набором
источников часов (`sources` без `sessions`: время в паре с ИИ в часы не входит — *принятое допущение*) и
тем же `hoursAlgo`; при смене — одна сноска («с недели #N учитываются локальные источники»).
Иначе первая неделя I1 выглядела бы ложным рекордом. Смену модели (`llm`) только помечаем, ряд не рвём.
Формулы — в [../trends/02-computation.md](../trends/02-computation.md).

## Корректирующие записи

Корректирующий отчёт `<день>_local.md` несёт такую же запись с `kind: "corrective"`; state он не меняет, и в
`history` его запись не попадает.

- Строит локальный сборщик тем же `buildWeekRecord`. `<день>` — день основного отчёта той же недели, `n` —
  её номер, `sources: ["local"]`, в `projects[]` — только то, чего нет в основном отчёте.
- `hoursScale: "union-with-main-report"` — минуты посчитаны на общей шкале времени с коммитами основного
  отчёта, поэтому ретроспектива вправе сложить часы двух файлов. *Принятое допущение:* поле названо в
  решениях по ретроспективам, а в общей схеме его не было — добавлено как необязательное.
- *Принятое допущение:* `prs`, `issues`, событийные счётчики, `ci`, `deployments` равны 0, `achievements`
  пуст, `streak` равен 0 — у `corrective` читатели эти поля не смотрят.
- В недельный мини-график такие записи не попадают (недели до I1 на нём занижены); ретроспектива читает
  файл сама и показывает одну неделю работы — [../retrospectives/02-pipeline.md](../retrospectives/02-pipeline.md).

**Черновая форма v0.** Три уже лежащих файла (и те, что выйдут до R0) несут одну строку
`<!-- achievements-record {"v":0,"kind":"local-addendum",…} -->`. R1 переводит их в v1 в клоне
репозитория отчётов; видимый текст не меняется, в diff — только замена последней строки на блок из трёх.

| Было в v0 | Станет в v1 |
|---|---|
| маркер `achievements-record`, одна строка | маркер `achievements:record`, три строки |
| `kind: "local-addendum"`, `week` | `kind: "corrective"`, `n` |
| `mainReport` | убирается: пара находится по имени файла |
| `since`, `until`, `commits`, `hoursScale` | без изменений; добавляется `days` |
| `additions`, `deletions` (уже «сырые − загруженные») | без изменений |
| `importedAdditions` | поля нет: число остаётся в видимой сноске файла *(принятое допущение)* |
| `focusedHours` | `minutes` — сумма `focusedMinutes` по проектам |
| `repos[]: { name, …, focusedMinutes }` | `projects[]: { name, …, minutes, local: true, private: true }` — любой локальный репозиторий приватный |
| `model` | `llm` |
| нет | `generatedAt` — время коммита файла; `tz`, `privacy` — параметры скрипта; `sources: ["local"]`; `hoursAlgo: 1`; `capped: false`; `est: [0, 0]`; `activeDays` — по спискам коммитов в файле, как в бэкфилле; `dayMap` и `late` не пишутся; `src: "backfill"` |

## Какая запись главная: правило для внешних инструментов

Worker'у это правило не нужно (его главный список недель — `history`); оно для скриптов, читающих архив отчётов без state.

Запись O вытеснена, если есть запись N того же `kind`, у которой `N.generatedAt > O.generatedAt` и
`N.since ≤ O.since < N.until`. Файл без блока для инструментов невидим.

| Случай | Итог |
|---|---|
| Неделя выпущена дважды в разные дни (дубль недели №7) | Побеждает поздняя: после отката повтор стартует с того же `since` |
| Двойной откат | Поздняя запись накрывает обе ранние |
| Недели №1 и №2 пересекаются на день | Обе остаются: начало первой лежит вне периода второй |

Известный предел: если после отката неделю не перезапускали дольше 4 недель, `since` повтора обрезан окном
догона (`src/run.ts:25-38`), и сирота останется «главной» — такой случай скрипт печатает отдельно.
