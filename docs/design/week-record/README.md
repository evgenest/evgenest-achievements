# Запись недели: машинная память отчёта

> **Для кого:** владелец проекта и тот, кто будет писать код итераций R0 и R1.
> **Что здесь решает владелец:** три пункта общего списка — №5 (часы становятся видны и при выключенной
> оценке зарплаты), №7 (дописать невидимую запись в старые отчёты), №9 (порог массового коммита).
> Сами вопросы и рекомендации — только в [общем README](../README.md).
> **Что просто к сведению:** всё остальное — где лежит запись, что меняется в коде, как проверяется.

Статус: **дизайн, код не написан**. Дата: 2026-09-19. Основа трендов ([../trends/](../trends/README.md))
и ретроспектив ([../retrospectives/](../retrospectives/README.md)).

## Главное за минуту

Каждый недельный прогон один раз собирает маленькую машинную запись о неделе и кладёт её туда, куда и так
пишет; ничего нового заводить не нужно.

- **Что это.** Около 2 КБ JSON: числа недели, минуты по проектам, счётчики событий PR и issues, пометки
  «каким методом и из каких источников посчитано». Схема — в [01-schema.md](01-schema.md).
- **Где лежит.** Невидимым комментарием в конце файла отчёта (вечный архив) и в поле `history` снимка
  state (рабочая копия последних 53 недель). State — счётчики проекта в KV, хранилище «ключ — значение»
  Cloudflare; каждый прогон дописывает туда новый снимок.
- **Почему срочно.** Сырьё не хранится. Каждая пятница без R0 навсегда теряет минуты по проектам и
  счётчики событий: задним числом их взять неоткуда.
- **Что увидит владелец.** Ничего: видимый текст отчёта не меняется. Форк без новых переменных получает
  запись молча.
- **Откат** `DELETE /state/latest` убирает и запись последней недели — без единой строки особого кода.
- **Сбой** сборки записи — одна строка в логе; отчёт и state выходят как раньше.
- **Прошлое.** R1 делает бэкфилл (backfill) — восстанавливает из старых отчётов записи недель, вышедших
  до R0 (сегодня их 8), с честными потерями, — и даёт страховочный скрипт на случай потери KV:
  [02-backfill-and-recovery.md](02-backfill-and-recovery.md).

## Зачем: принципы P1–P3

Запись недели — прямое следствие решения «сырьё не хранить»; полные формулировки принципов — в
[общем README](../README.md).

| Принцип | Коротко | Что из него следует здесь |
|---|---|---|
| **P1** | Долгая память проекта — готовые отчёты. Текст коммитов после отчёта нигде не остаётся; KV — транзитный буфер | Тренды и ретроспективы не могут «перечитать неделю заново» — её уже нет |
| **P2** | Всё, что когда-нибудь понадобится, записывается в момент сборки отчёта | В записи есть поля, которые сегодня никто не читает (`est`, `tz`, `cost`): позже их не восстановить |
| **P3** | Запись живёт в двух местах, которые и так пишутся | Ни нового хранилища, ни файла-указателя, ни нового ключа KV, ни одного внешнего запроса |

Без записи трендам пришлось бы разбирать русский текст отчёта, а минут по проектам в отчёте нет вовсе.

## Как запись едет внутри файла отчёта

Запись — последний блок того же файла `<REPORTS_DIR>/<день>.md`, поэтому пишется тем же одним запросом
записи, что и отчёт, и разойтись с ним не может.

```
…последняя строка видимого отчёта…

<!-- achievements:record
{"v":1,"kind":"week","n":12,"since":"…","until":"…", …}
-->
```

- Три строки: маркер `<!-- achievements:record`, JSON **одной строкой**, закрывающая `-->`.
- Внутри JSON символы `<` и `>` пишутся как `\u003c` и `\u003e`, а последовательность `--` — как
  `-\u002d`. Это остаётся правильным JSON (`JSON.parse` возвращает исходные строки), а комментарий не
  может закрыться раньше времени. Проверочное имя для теста: `a-->b<!--`.
- Читатель `extractRecord(md)` берёт **последнее** вхождение маркера, ближайшую за ним `-->`, разбирает
  JSON и проверяет версию. Запись читается, только если её блок — последнее непустое содержимое файла:
  строка маркера начинается с начала строки, а `-->` — последняя непустая строка. Иначе маркер внутри
  видимого текста в неделю без записи сошёл бы за настоящую запись. При любой ошибке читатель возвращает
  «записи нет» и никогда не бросает исключение.
- «Невидимый» значит «GitHub не показывает его на странице отчёта». В сыром файле комментарий виден
  любому, у кого есть доступ к репозиторию отчётов. Поэтому запись строится только из недели **после**
  политики приватности (принцип P4) — подробно в [01-schema.md](01-schema.md#приватность-что-попадает-в-запись).

## Как запись едет внутри state

Рабочая копия — два необязательных поля на верхнем уровне `AppState`; они пишутся тем же `STATE.put`, что и
счётчики, и откатываются вместе с ними.

```ts
// src/types.ts, AppState — оба поля необязательные: state старого форка читается без ошибок
history?: WeekRecord[];   // не более 53 записей, старые первыми; запись с тем же n заменяется
career?: { minutes: number; weeks: number; activeWeeks: number };   // накопитель «с начала наблюдений»
```

- **53 записи внутри снимка** и **52 снимка в KV** (`HISTORY_LIMIT`, `src/state.ts:13`) — разные вещи.
  Снимок — состояние после одного прогона; внутри каждого лежит вся рабочая история.
- `career` нужен, потому что `history` обрезается на 53 неделях, а строка «с начала наблюдений: N ч»
  должна расти дальше. *Принятое допущение:* `minutes` — сумма `minutes` всех записей, `weeks` — сколько
  недель в неё вошло, `activeWeeks` — сколько из них с активностью.
- `career` лежит **не** внутри `allTime`. Причина проверена чтением кода: данные для модели собираются
  разворотом `{ ...state.allTime }` и `{ ...state.lastWeek }` (`src/sanitize.ts:167-168`), а защита бросает
  исключение на любом незнакомом ключе (`src/sanitize.ts:110-113`). Новое поле внутри `allTime` уронило бы
  недельный прогон; поле на верхнем уровне в данные для модели не попадает.
- `GET /state` по-прежнему отдаёт только ключи и метаданные снимков (`src/index.ts:67-70`); `StateMeta`
  не меняется.
- Размер (оценка по прототипам вариантов дизайна, на итоговой схеме не перемерено): запись 1,5–2,5 КБ;
  снимок растёт на 80–130 КБ; 52 снимка — 4–7 МБ. Пределы сверены с документацией Cloudflare: на бесплатном
  тарифе KV хранит 1 ГБ, одно значение — до 25 МиБ. Репозиторий отчётов за 10 лет — около +1 МБ.
- К сведению: при `PRIVATE_REPOS=full` в значении state теперь лежат имена проектов за 53 недели (раньше
  — только счётчики). Это вносится в раздел «данные в покое» в
  [../local-sources/08-threat-model.md](../local-sources/08-threat-model.md) и в `SECURITY.md`.

**`src/state.ts`.** `extras = { record?, local? }`. R0 вводит сигнатуру и поле `record`; I1 потом только
добавляет `local` (журнал учтённого). Сегодня `advanceState` собирает новый state из явного списка полей
(`src/state.ts:78-100`) и незнакомые теряет; **I0-минимум** меняет это: незнакомые поля верхнего уровня
переносятся как есть. R0 поверх этого ведёт `history` и `career`; когда записи нет (`record` равен `null`),
оба поля едут дальше без изменений.

**`src/run.ts`.** Порядок шагов; новое помечено:

1. Как сейчас: state → сбор → `applyPrivacy` (→ словарь замен, если он задан) → ачивки → шкала времени →
   модель и ставки → `resolveHours` → стоимость (`src/run.ts:30-63`).
2. **Новое, в своём `try/catch`:** `record = buildWeekRecord(...)` из уже обработанной недели, state и
   результата расчёта часов. Ошибка → строка лога `record_failed`, `record = null`.
3. (R2) блок «На дистанции» — отдельный `try/catch`, лог `trends_failed`.
4. `buildReport(...)` — как сейчас (`src/run.ts:65`).
5. Подметание видимого текста словарём замен — только если словарь задан (итерация A1).
6. **Новое:** `embedRecord(markdown, record)`, если запись есть.
7. `commitFile` — как сегодня: чтение `sha` и одна запись файла (`src/run.ts:68`, `src/github.ts:293-305`).
8. Telegram (`src/run.ts:70`).
9. `saveState(advanceState(state, week, ids, rates, { record }))` (`src/run.ts:71`).

Шаг 5 стоит **перед** шагом 6 намеренно: подметание по markdown со встроенной записью ломает JSON, если в
замене есть кавычки (проверено скриптом при разборе вариантов) — неделя молча исчезла бы из архива.
Строки записи уже взяты из обработанной недели. Итог для прогона: **+0** внешних запросов, **+0** записей
в KV, **+0** вызовов модели.

## Сбои, откаты, повторы

Новая часть может только ухудшить отчёт (нет записи), но не уронить его (принцип P5); привычный цикл
«прогон → откат → повтор» ничего не дублирует.

| Ситуация | Что происходит |
|---|---|
| `buildWeekRecord` бросил исключение | Лог `record_failed`; отчёт без блока; `history` и `career` едут дальше как были; в трендах эта неделя — пропуск |
| `since ≥ until` (ручной `/run?date=` в прошлое: `src/run.ts:36-38`, сегодня `src/index.ts:83-93` это не проверяет) | Запись не создаётся. I0-минимум добавляет ответ 409 на входе и ту же проверку внутри `runWeekly` (HTTP-обработчик и потребитель очереди могут видеть разный state, а очередь — доставить сообщение дважды): такой прогон выходит без записи отчёта, state и Telegram |
| Падение между `commitFile` и `saveState` | Как сегодня: повтор в тот же день перезапишет файл вместе с записью, state запишется один раз |
| `DELETE /state/latest` и повтор | Снимок уходит вместе с последней записью и с `career`; повтор добавит их заново. В тот же день файл перезапишется; в другой день старый файл останется сиротой — отчётом отменённого прогона, на который state больше не указывает |
| Файл-сирота (дубль недели №7) | Worker'у не мешает: главный список недель — `history`, а не список файлов. Правило для внешних инструментов — в [01-schema.md](01-schema.md#какая-запись-главная-правило-для-внешних-инструментов) |
| Откат деплоя на старый код · потеря KV | Код не старше I0-минимума `history` и `career` не стирает: они едут дальше целыми, без недель старого кода. Код старше I0-минимума и потеря KV их стирают; лечится `records-rebuild` — [02-backfill-and-recovery.md](02-backfill-and-recovery.md#деплой-старого-кода) |
| `reportCount > 0`, а `history` пуста или в ней нет записи прошлой недели (`n = reportCount`) | Лог `history_missing`; прогон идёт как обычно, видимый отчёт не меняется. В первом прогоне после R0 строка ожидаема. Пропажу записей, восстановленных бэкфиллом (двойной откат после него), так не увидеть — её показывает `records-rebuild --check` |

## Итерации

Две итерации: R0 начинает писать запись, R1 закрывает прошлое и даёт страховку; место в общем порядке —
в [общем README](../README.md).

**Перед R0 обязателен I0-минимум:** заморозка золотого отчёта (эталонный файл в тестах, с которым результат
сравнивается байт в байт); защита от мусорного прогона внутри `runWeekly` (`since ≥ until` или ручной прогон
короче суток → выход без записи отчёта, state и Telegram; ответ 409 в `/run` — ранняя подсказка человеку);
`advanceState` переносит незнакомые поля state; `max_concurrency: 1` (сегодня в конфигах wrangler его нет);
исключение репозитория отчётов из сбора. Иначе мусорный прогон — в том числе повторно доставленное сообщение
очереди — запишет в `history` «неделю» длиной в минуты, а откат деплоя сотрёт историю.

**R0 (размер M) — запись недели, `history`, `career`, даты PR и issues, правило массовых строк.** Приёмка:

- золотой JSON записи на богатом тестовом наборе; `embedRecord → extractRecord` возвращает исходный объект,
  включая имя `a-->b<!--`; маркер внутри видимого текста при отсутствующей записи → «записи нет»;
- отчёт отличается от золотого **только** блоком в конце (золотой перезамораживается один раз, осознанно);
- запись с `v: 2` читается как отсутствующая, но `appendHistory` переносит её без изменений;
- прогон на state с `history` и `career` не ломает защиту данных для модели; state старого форка без этих
  полей читается без ошибок;
- принудительная ошибка в `buildWeekRecord` → отчёт записан, state сохранён, в логе `record_failed`;
  прогон на state с `reportCount > 0` и пустой `history` → в логе `history_missing`, отчёт тот же;
- при `redact` имя приватного проекта в записи не встречается, приватные свёрнуты в `name: null`; при
  `skip` приватных чисел нет;
- PR, обновлявшийся две недели подряд, входит в `prs` обеих недель, но в `prsOpened` и `prsMerged` — по
  одному разу; `since ≥ until` → `null`; тесты на `days`, `late`, `bulk`, `dayMap`;
- блок не больше 4 КБ при 15 проектах; счётчик внешних запросов прогона не вырос.

**R1 (размер S–M) — бэкфилл недель, вышедших до R0 (сегодня 8), перевод корректирующих записей в v1, `records-rebuild`. Строго до
I1-T — той части итерации I1, где машина и Worker начинают обмениваться списком учтённого.** Приёмка — в
[02-backfill-and-recovery.md](02-backfill-and-recovery.md#приёмка-r1).

## Что отклонено

Все отклонённые варианты добавляли хранилище, внешний запрос или связность, без которых можно обойтись.

| Вариант | Почему нет |
|---|---|
| Файл-указатель недель или файл-сосед `<день>.json` | +2…4 внешних запроса, второй коммит (запись уже не едина с отчётом), не откатывается вместе со state |
| Отдельный ключ KV, D1, R2 | Новая сущность и настройка для каждого форка |
| Только KV, без копии в отчёте | Потеря KV или уход с Cloudflare стирают историю навсегда |
| Worker сам подгружает записи из репозитория отчётов | Два пути чтения, внешние запросы в недельном прогоне; заменено локальным `records-rebuild` |
| Устойчивый псевдоним приватного проекта (имя, подписанное секретом, — HMAC) | Новый секрет, а в возможно публичном репозитории появляется связь «тот же приватный проект в неделях 3, 4, 7» |
| Раскладка коммитов по часам суток, личные рекорды в state | Восстановимо из git или из `history`; лишнее раскрытие и лишние поля |
| Служебный маршрут «дописать историю» в Worker'е | Ещё один служебный адрес, который пришлось бы защищать, — ради одного раза; заменено локальным скриптом |

## Журнал решений

Все решения приняты в один день — по итогам сравнения трёх вариантов дизайна и их независимой проверки.

| Дата | Решение | Почему |
|---|---|---|
| 2026-09-19 | Запись недели создаётся в момент сборки отчёта | Сырьё не хранится (P1); позже взять неоткуда (P2) |
