# 02. Прошлые недели и восстановление истории

> **Для кого:** владелец (он сам выполняет команды из этого документа) и тот, кто пишет скрипты R1.
> **Что здесь решает владелец:** дописывать ли невидимую запись в старые отчёты (сегодня их 8) — вопрос №7 в
> [общем README](../README.md); рекомендация — да. Работает и без этого.
> **Что просто к сведению:** порядок действий, защита от гонки с пятничным запуском, что делать при потере KV
> и после деплоя старого кода. Все адреса и имена — заполнители.

Статус: **дизайн, скриптов ещё нет.** Итерация R1; Worker в ней не меняется — всё делается локально.

## Главное за минуту

Прошлое закрывается двумя локальными скриптами: один раз восстановить записи недель, вышедших до R0
(бэкфилл, backfill), и в любой момент уметь пересобрать историю из архива отчётов.

- `scripts/backfill-history.ts` разбирает отчёты всех недель, вышедших до деплоя R0 (на 2026-09-19 их 8), и
  готовит новый снимок state, в чью `history` добавлены восстановленные записи. В KV его кладёт владелец
  одной командой `wrangler kv key put`; отмена — привычный `DELETE /state/latest`.
- Какие недели настоящие, решает **state**, а не список файлов: файлы переписывались при тестах.
- Восстановить удаётся не всё: минут по проектам в старых отчётах нет — в записи честно стоит `null`.
- Главная опасность — гонка с пятничным запуском. Скрипт запоминает, от какого ключа построен файл, и
  отказывается печатать команду, если state с тех пор изменился. Правило для человека: **не в пятницу утром**.
- `scripts/records-rebuild.ts` — страховка: собирает `history` заново из встроенных записей в клоне
  репозитория отчётов. Нужен после потери KV и после отката деплоя на код старше I0-минимума (он стирает историю).
- Всё это делается **строго до** транспорта локальных источников (I1-T).

## Что удаётся восстановить из старого отчёта

Числа берутся ровно такими, какими владелец видел их в отчёте; чего в отчёте нет — не выдумывается.

| Поле записи | Откуда | Точность |
|---|---|---|
| `n` | число после `#` в заголовке; обязано совпасть с `reportCount` снимка | точно |
| `until`, `generatedAt`, `streak` | метаданные снимка: `until`, `savedAt`, `streak` (`src/state.ts:27-32`) | точно |
| `since` | `until` предыдущей настоящей недели; у недели №1 — `until` минус 7 суток, как считает `src/run.ts:36-38`. Если первая дата в строке периода файла с этим не сходится, берётся дата из файла, расхождение печатается | *принятое допущение* |
| `commits`, `prs`, `issues`, `additions`, `deletions`, `ci`, `deployments`, `activeRepos` | таблица итогов, строки 1–8 по позиции (`src/report.ts:51-65`) | как в отчёте |
| `projects[]` | таблица проектов по позиции столбцов (`src/report.ts:71-79`); `minutes: null` | как в отчёте; минут нет |
| `minutes` | первая строка раздела стоимости («~N ч», `src/report.ts:132`) × 60 | до 6 минут: часы округлены до 0,1 |
| `cost` | вторая и третья строки того же раздела, только цифры; валюта — параметр скрипта | как в отчёте |
| `activeDays`, `bulk` | списки коммитов под `<details>`: число разных дат и пары «(+N/−M)» (`src/report.ts:99`) | по дате коммиттера; у скрытых репозиториев списков нет — оценка снизу |
| `achievements` | названия из раздела ачивок → id обратным поиском по `src/i18n` | точно |
| `llm` | строка-подпись в конце (`src/report.ts:175`) | точно |
| `prsOpened` … `issuesClosed` | приближённо: PR «открыт» в неделю, где его ссылка впервые появилась в отчётах, «слит» — где он впервые показан `[merged]` (`src/report.ts:112`); issues — так же по `[closed]` | приближённо |
| `hoursAlgo` | `0` для недель №1–№6, `1` с недели №7 — параметр скрипта | см. ниже |
| `privacy`, `tz` | параметры скрипта: в отчёте их нет, владелец их знает | — |
| `est`, `capped`, `late`, `dayMap` | не восстановить: `est: [0, 0]`, `capped: false`, `late` и `dayMap` не пишутся | нет |

- Каждая такая запись помечена `src: "backfill"`.
- **`hoursAlgo`.** `src/hours.ts` появился 2026-09-12; до него часы недели были одной цифрой от модели.
  *Принятое допущение:* прежний метод получает номер `0`, нынешний — `1`. Из-за правила разрыва ряда
  «обычное» значение в трендах считается только с недели №7.
- **Флаг `private`.** Из markdown не видно, какой проект приватный. *Принятое допущение:* при режиме `full`
  все поимённые проекты восстановленных недель получают `private: true` — при сомнении скрыть. Пока режим
  не ужесточён, это ни на что не влияет.
- **Репозиторий отчётов.** В старых отчётах он сам числится проектом недели (коммиты робота). *Принятое
  допущение:* скрипт убирает эту строку из `projects[]` (параметр `--reports-repo`), итоги не трогает —
  иначе у трендов появилась бы ложная серия «N-я неделя подряд».
- Недели без раздела стоимости (у владельца таких нет) в `history` не попадают и печатаются списком
  пропущенных: `minutes` — обязательное поле, а выдумывать его нельзя. *Принятое допущение.*

## Какие недели настоящие: список из state

Главный список недель берётся из сохранённого ответа `GET /state`, а не из списка файлов: в репозитории
отчётов есть дубль недели №7 и пересечение недель №1 и №2.

1. Вход — ответ `GET /state`: `{ current, versions: [{ key, meta: { savedAt, until, reportCount, streak } }] }`
   (`src/index.ts:67-70`). Значений state в нём нет, только ключи и метаданные.
2. Для каждого номера отчёта берётся **последний** по `savedAt` снимок → его `until` → файл
   `<REPORTS_DIR>/<день until по UTC>.md` (так имя строит `src/run.ts:66-67`).
3. Номер в заголовке файла обязан совпасть с `reportCount`. Не совпал — понятное сообщение и остановка.
4. Снимки отменённых прогонов уже удалены откатом, поэтому на файл-дубль недели №7 не указывает ни один
   снимок — он пропускается сам.
5. Неделя, чья запись уже лежит в `history` текущего state (её написал R0), пропускается.
6. Требования «сумма записей = all-time» **нет**: на настоящих данных она не сходится (файлы переписывались
   при тестах). Расхождение печатается как известное. Пересечение недель №1 и №2 тоже печатается и не чинится.

## Как разбирается отчёт

Разбор идёт по позиции строк и столбцов, а не по русским подписям, и защищён тестом «туда и обратно».

- Порядок строк таблицы итогов и столбцов таблицы проектов жёстко задан в `src/report.ts`. Разделы стоимости
  и ачивок находятся по заголовкам из `src/i18n` для языка `--lang`.
- Числа в русской локали пишутся с **неразрывными пробелами** между разрядами (`toLocaleString`,
  `src/report.ts:29`), а в списках коммитов стоит типографский минус «−». Разборщик убирает любые пробельные
  символы внутри числа, включая U+00A0 и U+202F.
- Даты в списках не разбираются: для `activeDays` достаточно посчитать разные строки дат.
- Тест: `buildReport(тестовый набор)` → разбор → те же значения, что у `buildWeekRecord` на том же наборе, по
  всем восстановимым полям; для `ru` и `en`. Он же ловит расхождение после будущих правок вёрстки отчёта.
- Разборщик — общий модуль для обоих скриптов. Это одноразовый инструмент: после крупной переделки отчёта
  его проще удалить, чем чинить.

## Порядок действий

Шесть шагов; сеть нужна в шагах 1 и 3–6; скрипт сам ничего не пишет ни в KV, ни в репозиторий отчётов.

```sh
# 1. Снять вход (не в пятницу утром — см. следующий раздел)
curl -s -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/state > metas.json
wrangler kv key get "<current из metas.json>" --binding STATE --remote --text -c <wrangler-config> > state.json
git clone <reports-repo-url> reports-clone
# 2. Собрать файл
bun scripts/backfill-history.ts prepare --metas metas.json --state state.json --reports reports-clone \
  --lang ru --tz <TIMEZONE> --privacy <режим> --currency <валюта> --hours-algo-1-from 7 \
  --reports-repo <owner>/<reports-repo> [--patch-reports]
#   → таблица «неделя → файл → числа» для проверки глазами
#   → state.backfilled.json и state.backfilled.basis.json (от какого ключа построено)
# 2б. Перевести корректирующие записи из черновой формы в v1 (форма команды — принятое допущение)
bun scripts/backfill-history.ts convert-corrective --reports reports-clone
# 3. Прямо перед записью — свежий список и сверка
curl -s -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/state > metas.fresh.json
bun scripts/backfill-history.ts verify --basis state.backfilled.basis.json --metas metas.fresh.json
#   → ключ тот же: печатает готовую команду шага 4;  ключ другой: отказ
# 4. Выполнить напечатанную команду
wrangler kv key put "state:<сейчас, ISO>" --path state.backfilled.json --binding STATE --remote \
  -c <wrangler-config> --metadata \
  '{"savedAt":"<сейчас, ISO>","until":"<как у текущего>","reportCount":<тот же>,"streak":<тот же>}'
# 5. Проверить; при любом сомнении — отменить
curl -s -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/state            # current — новый ключ
curl -s -X DELETE -H "Authorization: Bearer <RUN_SECRET>" https://<worker-url>/state/latest   # отмена
# 6. Только если были --patch-reports или convert-corrective: посмотреть и отправить правки
git -C reports-clone diff --stat      # ожидаем: только строки в конце файлов, видимый текст не тронут
git -C reports-clone commit -am "records: v1" && git -C reports-clone push
```

- Новый снимок — это текущий state, в чью `history` **добавлены** восстановленные записи (слияние по `n`;
  запись, написанную R0, бэкфилл не заменяет); счётчики, серия, ставки не меняются. *Принятое допущение:*
  `career` = прежний `career` + суммы восстановленных записей.
- Метаданные обязательны: по ним `GET /state` и сам бэкфилл строят список (`src/state.ts:44-45, 107-112`).
- Флаги `--path`, `--metadata`, `--binding`, `--remote`, `--text` сверены со справкой wrangler 4,
  установленного в проекте. На живом KV команда не выполнялась.

## Гонка с пятничным запуском

Если между шагом 1 и шагом 4 пройдёт недельный прогон, бэкфилл молча откатит его — поэтому скрипт сверяет
ключ, а человек выбирает спокойное время.

**Что именно ломается.** Прогон пишет снимок новее того, что мы прочитали. Наш ключ `state:<сейчас>` ещё
новее и становится текущим: `loadState` берёт последний по алфавиту ключ (`src/state.ts:52-57`). Но внутри
него — старые `reportCount` и `lastRunUntil`. Следующая пятница посчитает ту же неделю второй раз и выдаст
уже занятый номер отчёта. Ошибки при этом нигде не будет.

| Защита | Что делает |
|---|---|
| Файл `…basis.json` и шаг `verify` | Скрипт запоминает ключ, от которого построен файл, и печатает команду записи, только если в свежем `GET /state` поле `current` то же |
| Правило «не в пятницу утром» | Запуск по расписанию — пятница, 08:00 UTC (`crons` в конфиге wrangler). Список ключей KV может отставать до ~60 секунд, так что сверка сразу после прогона способна его не увидеть. Не запускать бэкфилл в пятницу до полудня UTC и в первые 5 минут после ручного `/run` |
| Шаг 5 | После записи `current` — наш ключ, а `reportCount` и `until` те же, что были |
| Отмена | Прогон всё же проскочил (в списке есть ключ новее базового с большим `reportCount`): `DELETE /state/latest` снимает именно бэкфилл — он самый новый, — и снимок прогона снова текущий. Затем всё заново с шага 1. Оборотная сторона: снимок бэкфилла — обычное звено цепочки, и двойной откат, сделанный позже, снимает вместе с неделей и его — восстановленные записи пропадают молча. Проверка — `records-rebuild --check`, лечение — `records-rebuild` |

Прогон **после** шага 4 безопасен: он строится уже поверх state с историей. `max_concurrency: 1` здесь не
помогает: запуск по расписанию идёт мимо очереди.

## Невидимые записи в старых отчётах и перевод корректирующих

Обе правки меняют только невидимый хвост файлов в клоне; коммит и push делает владелец.

- `--patch-reports` (вопрос №7) дописывает те же восстановленные записи блоком в конец старых отчётов. `git diff`
  показывает только добавленные строки в конце файлов. Без ключа всё работает, но `records-rebuild` для этих
  недель будет заново запускать разборщик markdown вместо чтения готовой записи.
- Подкоманда `convert-corrective` проходит по всем `*_local.md` с записью черновой формы v0 (три лежащих
  файла и те, что выйдут до R0) и заменяет последнюю строку блоком v1 — таблица соответствия в
  [01-schema.md](01-schema.md#корректирующие-записи). Видимый текст не меняется.
- Ручной коммит шага 6 не должен попасть в следующий отчёт как «работа недели» — поэтому исключение
  репозитория отчётов из сбора (I0-минимум) идёт раньше R1.

## `records-rebuild`: история из архива

Скрипт читает встроенные записи из клона репозитория отчётов и собирает `history` и `career` заново — это
страховка от двух бед ниже.

- Читает `<REPORTS_DIR>/*.md`, кроме `*_local.md`, `monthly/`, `yearly/`: корректирующие записи в `history`
  не входят. Из каждого файла — `extractRecord`; затем правило «какая запись главная»
  ([01-schema.md](01-schema.md#какая-запись-главная-правило-для-внешних-инструментов)): state, по которому
  можно сверить список недель, в этой ситуации может и не быть.
- `history` — последние 53 записи по `n`; `career` — сумма по **всем** настоящим записям, не только по 53.
- Файлы без блока печатаются списком «нет записи»; их можно закрыть разборщиком:
  `backfill-history.ts prepare --weeks <номера>` (записи получат `src: "backfill"`).
- Основа нового снимка — текущий state из KV; меняются только `history` и `career`. Дальше те же шаги 3–5:
  сверка ключа, та же команда `wrangler kv key put`, та же отмена.
- Режим `--check` ничего не пишет: печатает сирот, пропуски и расхождения с `history` из state.

### Потеря KV

Если пространство KV пересоздано или форк переехал, history нужно восстановить **до** ближайшего прогона,
иначе нумерация начнётся с единицы.

- Признак: `GET /state` отдаёт `current: null`. Прогон на пустом state даст отчёт №1 за последние 7 суток
  (`src/state.ts:15-24, 59`, `src/run.ts:36-38`), а его запись №1 потом вытеснит настоящую (замена по `n`); если
  такой прогон уже случился — сначала `DELETE /state/latest`.
- `records-rebuild.ts prepare --from-scratch` собирает state целиком из записей. *Принятое допущение:*
  `reportCount` — наибольший `n`; `streak` — из последней записи; `bestStreak` — наибольший `streak`;
  `unlocked` — объединение `achievements`; `lastRunUntil` — последний `until`; `lastWeek` — числа последней
  записи; `allTime` — суммы по записям (с известным расхождением со старой строкой «All-time» — оно
  печатается); `rates: null` — ставки найдутся заново при следующем прогоне.
- После I1 вместе с KV теряется и журнал учтённого (ledger) — что с ним делать, описано в
  [05-operations](../local-sources/05-operations.md#откат-деплоя-и-потеря-kv).

### Деплой старого кода

С I0-минимума откат деплоя `history` и `career` не стирает; стирает их только код старше I0-минимума — тогда
после возврата нового кода нужен `records-rebuild`.

- **Код не старше I0-минимума:** `advanceState` переносит незнакомые поля верхнего уровня state как есть — оба
  поля едут дальше целыми, но без недель старого кода.
- **Код старше I0-минимума** собирает state из явного списка полей (`src/state.ts:78-100`, проверено чтением
  кода) и на первом же прогоне молча стирает оба поля. Лечение — `records-rebuild`.
- В обоих случаях недели, вышедшие на коде старше R0, не имеют встроенной записи — это пропуски; они
  закрываются разборщиком (`--weeks`), с потерями как у бэкфилла, после чего `records-rebuild` пересчитывает `career`.
- Откат на код **после** R0 безопасен: записи незнакомой версии `appendHistory` переносит как есть.
- Журнал учтённого (после I1) подчиняется тому же правилу, но лечится иначе; все правила отката собраны в
  [05-operations](../local-sources/05-operations.md#откат-деплоя-и-потеря-kv).

## Почему строго до I1-T

Бэкфилл добавляет в цепочку state снимок, который не является прогоном, а транспорт локальных источников
рассчитывает, что каждый снимок — прогон.

- **«Грейс».** После I1-T Worker публикует список учтённого по state, который был **до** последнего прогона, —
  поэтому текст последней отчитанной недели живёт в KV ещё один цикл. Лишний снимок сдвигает цепочку: текст
  уйдёт на цикл раньше, и привычный «откат + немедленный перезапуск» потребует сначала push с машины.
- **Смысл отката.** `DELETE /state/latest` на один цикл означал бы «снять бэкфилл», а не «снять неделю».
- До I1-T ни списка учтённого, ни «родословной» снимков нет — лишний снимок безвреден.
- `records-rebuild` после I1-T остаётся аварийной мерой с той же ценой — один цикл без «грейса»; список
  учтённого Worker пересоберёт сам, увидев незнакомый ключ state. *Принятое допущение:* решения от 2026-09-19 этот
  случай не описывают. Подробности — [07-selection](../local-sources/07-selection.md#грейс-отсрочка-в-один-прогон).

## Приёмка R1

Приёмка — тесты на выдуманных данных плюс одна проверка глазами на данных владельца.

- Тест «туда и обратно» на **выдуманном** отчёте, `ru` и `en`, включая числа с неразрывными пробелами.
- Номер в заголовке не совпал с метаданными снимка → понятная ошибка и остановка.
- На данных владельца: восстановлены все недели, вышедшие до R0 (на 2026-09-19 их 8); записи, написанные
  R0, остались в `history` байт в байт; `career` вырос ровно на сумму восстановленных; файл-дубль недели №7 пропущен; пересечение недель №1 и №2 и
  расхождение с all-time напечатаны и не считаются ошибкой; таблица чисел совпадает с отчётами.
- `verify` отказывает, если `current` изменился между `prepare` и сверкой.
- После записи `GET /state` показывает новый снимок с прежними `reportCount` и `until`;
  `DELETE /state/latest` его отменяет.
- Перевод корректирующих: видимый текст файлов не изменился ни на байт; новая запись читается `extractRecord`.
- Проверка на случайных сценариях (много случайных последовательностей прогонов и откатов):
  `records-rebuild(отчёты)` даёт ту же `history`, что велась по ходу.
- `--from-scratch` на клоне владельца: `reportCount`, серия и `lastRunUntil` совпадают с текущим state.

## Что останется неточным

Восстановленные недели беднее настоящих записей, и это видно в отчётах — скрывать не нужно.

| Что | Следствие |
|---|---|
| Минут по проектам за восстановленные недели нет | В ретроспективах за август и сентябрь раздел «куда ушло время» по проектам пуст |
| Часы недель №1–№6 посчитаны прежним методом | Отдельный ряд: с новыми неделями не сравниваются |
| Событийные счётчики PR и issues приближённые | Возможен сдвиг события на соседнюю неделю |
| `activeDays` — по дате коммиттера и без скрытых репозиториев; `dayMap` нет | «Активные дни» месяца для этих недель — сумма недельных значений; пятница на границе может быть учтена дважды |
| Корректирующие записи в `history` не входят | Недели №6–№8 на недельном графике занижены; ретроспектива показывает их полностью |
| Пересечение недель №1 и №2 на день | Остаётся как есть |
